### 1.3 抽樣是人為均衡的，不代表真實案量

序號 × 年度交叉比對後發現，**檔案序號決定法條依據，五年高度固定**：

```
序號    110    111    112    113    114
01-02  77(1)  77(1)  77(1)  77(1)  77(1)
03-04  77(2)  77(2)  77(2)  77(2)  77(2)
05-06  77(3)  77(3)  77(3)* 77(3)  77(3)
07-08  77(4)  77(4)  77(6)* 77(4)  77(4)
09-10  77(6)  77(6)  77(7)* 77(6)  77(6)
11-12  77(7)  77(7)  77(8)* 77(7)  77(7)
13-14  77(8)  77(8)  77(8)  77(8)  77(8)
15-17  79I    79I    79I    79I/II 79I
18-20  81I    81I    81I    81I    81I
21      —      —      —      —    複合案
                      * 112 年無 77(4) 案，自 #07 起整體位移一格
```

**每年固定 14 件程序（§77）＋ 3 件駁回（§79）＋ 3 件撤銷（§81）。**

> 🚫 **禁止在簡報上宣稱「69% 的訴願案是程序不受理」。**
> 70/101 是出題方抽樣模板的比例（14/20 = 70%），不是新北市真實案量。評審席可能有訴願審議委員，他們手上有真實統計，一講就破。
>
> 要提就寫：「本樣本 70/101 為程序不受理；樣本為出題方均衡抽樣，不代表實際案量分布。」

**可以講、而且無懈可擊的版本**：

> 程序審查是訴願法強制的前置關卡。**100% 的案件都必須先確認 §77 八款無一成立**，才能進入實體審查。這是條文結構（先程序、後實體），不是統計推論。

### 1.4 §77 是「排除性確認」，不是「八道依序通過的關卡」

條文原文：

> 第 77 條　訴願事件有左列各款情形**之一**者，應為不受理之決定

「之一」= 任一款成立即不受理。這是「或」的邏輯。

**對設計的意義**：系統不是讓承辦人逐款審八次，而是把他腦中「一眼排除」的隱性判斷變成**有紀錄的排除**（哪一款、依據什麼事實、誰確認的），並且：
- 真正要算的（期間）算對
- 真正難的（第 3、8 款）標黃轉人

> ⚠ **未驗證假設**：法制局現行的程序審查是否確實為「隱性一眼排除」，我們沒有證據。上述價值主張建立在這個假設上，簡報時應以假設形式陳述，或賽前向法制局確認。

### 1.5 論理結構實驗：款別 ≫ 案件類型

對 67 件單款不受理案，抽出理由欄引用的「法規名＋條號」集合，計算兩兩重疊度（交集 ÷ 聯集）：

| 配對方式 | 平均重疊度 |
|---|---|
| 同 **§77 款別** | **0.319** |
| 同 **案件類型**（噪音／廢棄物／洗錢…） | 0.167 |
| 全體隨機 | 0.137 |

**案件類型幾乎不帶訊號**（0.167 vs 隨機 0.137，只高 22%）。**款別帶強訊號**（隨機的 2.3 倍、案件類型的 1.9 倍）。

各款內部重疊度：

```
第6款 處分已不存在  0.703   ← 論理骨架幾乎相同
第7款 重行提起      0.307
第2款 逾期          0.303
第1款 程式不合      0.266
第3款 當事人不適格  0.216
第4款 無訴願能力    0.204
第8款 非行政處分    0.194   ← 最發散，也最難
```

**這條實驗直接決定檢索設計（見 §4.2）。**

## 2. 系統定位

### 2.1 TA（使用者）

| 層級 | 對象 | 在意什麼 |
|---|---|---|
| **主** | 新北市法制局 **訴願審議承辦人** | 少做重複苦工、不要判錯被撤銷 |
| 次 | **訴願審議委員會委員** | 論理有沒有漏洞、引用對不對 |
| 三 | 法制局主管 | 量能管考、品質一致性 |

**明確不是 TA：訴願人／一般民眾。** 這是內部輔助工具，不是對外服務。做成「民眾自助查詢」即偏題。

### 2.2 系統的紅線

1. **系統不做決定，只交出有出處的草稿。** 決定權 100% 在承辦人與委員會。
2. **「不確定」是一等公民輸出。** 抽不到事實、或落在困難法律判斷，一律標黃轉人，不准猜。
3. **每個事實主張都要有出處。** 抽出的欄位標頁碼行號，推出的結論標條文。

## 3. 架構

### 3.1 兩階段流程（承會議筆記）

```
訴願書 + 原處分 + 卷證
        │
        ▼
  【擷取層】 LLM 抽成 typed schema，每欄標來源
        │
        ▼
  【階段一：程序審查】§77 八款排除性確認
        │
        ├─ 任一款成立 ─→ 不受理草稿（理由四段 + 教示）─→ 承辦人審核
        │
        └─ 八款皆不成立
                │
                ▼
  【階段二：實質審查】爭點定位 → 法規/判解檢索 → 版本時效檢查
                │
                ▼
        駁回 或 撤銷 草稿（事實欄 + 理由欄）─→ 承辦人審核
                │
                ▼
        【稽核層】規則版本 + 判斷依據 + 人工修改紀錄
```

### 3.2 七層分工：哪幾層是檢索，哪幾層不是

> **檢索增強生成（RAG）**——先從文件庫撈出幾段相關文字，再連同問題交給語言模型請它照著回答，目的是讓模型不要憑空編造。這是目前文件問答的預設做法，**這場比賽多數隊伍都會用**。

| 層 | 是 RAG？ | 理由 |
|---|---|---|
| §77 八款判定 | ✗ | 純函式，輸入是擷取層的欄位 |
| 期間計算 | ✗ | 日期算術，10 件官方算式當測試 |
| 法規版本／時效警示 | ✗ | 兩份文件中繼資料的關聯比對，該事實未被寫在任何文件裡 |
| 教示填入 | ✗ | 規則：結果 + 決定年份 |
| **法條推薦清單** | **✓** | 就是檢索 |
| **相似案例** | **✓** | 檢索，但軸是款別不是類型（見 §4.2） |
| **實體案理由欄論述** | **✓** | 就是生成 |

**七層裡三層是 RAG。上台這樣講，不要宣稱「我們不是 RAG」——一問就破。**

定位句：

> **我們不是不用 RAG，是不讓 RAG 做它做不到的事。**
> 一般做法是「檢索完，讓模型判斷」；我們是「先判斷，再決定要檢索什麼」——模型只負責舉證，不負責判斷。
> 可以這樣做，是因為**答案的結構是法律先寫好的**：訴願法第 77 條就白紙黑字列著八款，不需要用檢索去「發現」它。

## 4. 會議筆記的三處修正

### 4.1 🔴 法律錯誤：「上報機關是否正確」不是不受理事由

**筆記原文**：階段一做「初步條件檢核（例如：是否在 30 天內提出、**上報機關是否正確**等）」。

**訴願法 §14 IV 原文**：

> 訴願人誤向原行政處分機關或受理訴願機關以外之機關提起訴願者，**以該機關收受之日，視為提起訴願之日**。

**誤向錯誤機關提起仍然有效**，法律效果只是改用該機關收受日當作提起日。它是**期間計算的一個輸入參數**，不是一道閘門。

**照筆記做會發生什麼**：系統對本來合法的訴願作出不受理判定 → 剝奪人民訴願權 → 被行政法院撤銷。

**修正**：把「收受機關」放進期間模組的輸入欄位，用來決定「提起日」取哪一個日期，不要做成 gate。

### 4.2 🟡 「切段比對相似度」會沿著錯的軸走

**筆記原文**：「將訴願文件與法規進行切段比對（例如：第 1-50 行對應特定法規），逐段檢驗相似度與關聯性」。

**問題**：§1.5 實驗證明，案件類型（表面文字）幾乎不預測論理結構（0.167 vs 隨機 0.137）。而中文法律文本的向量檢索會沿著「噪音／廢棄物／洗錢」這些表面詞走——**等於在一條幾乎沒有訊號的軸上做檢索**。

**修正**：檢索用兩層——

1. **硬過濾**（結構化，不用向量）：§77 款別 ＋ 案件類型 ＋ 處分類型
2. **桶內排序**（語意）：在過濾後的桶裡才做相似度排序

「切段 + 標行號」這個做法本身是對的，要保留——它是引用可追溯的基礎。錯的只是「用純相似度決定對應哪條法規」。

### 4.3 🟡 「未通過 → 直接產出不受理，案件結束」太危險

**筆記原文**：「若程序不符，系統直接產出『不受理』的理由與說明，**案件結束**」。

**問題**：§77 第 3 款（當事人適格）與第 8 款（是否為行政處分）是行政法上出了名難的兩個問題，合計 24 件（佔不受理案 34%），且論理重疊度最低（0.216 / 0.194），代表每件都要獨立判斷。

**修正**：

```
機械型款別（1、2、4、6、7）  → 🔴 高信心判定，產出草稿，承辦人審核
實質判斷款別（3、8）          → 🟡 標黃：定位爭點 + 檢索判解 + 交人決定
```

**「案件結束」的主體永遠是承辦人與委員會，不是系統。** 這句話在簡報上要明講，它是政府採用的前提。

```jsonc
  "evidence_refs": ["送達證書", "訴願書收文條碼"],
  "rule_version": "sha256:a3f2...",   // 稽核用，見 §6.6
  "short_circuit": true
}
```

`outcome` 五種狀態的語意：

| 狀態 | 意思 | UI |
|---|---|---|
| `NOT_TRIGGERED` | 這款不成立 | 🟢 |
| `TRIGGERED` | 這款成立 → 不受理 | 🔴 |
| `NOT_APPLICABLE` | 本案不適用（如個人訴願人 vs 第 5 款） | ⚪ |
| `INSUFFICIENT_EVIDENCE` | 缺必要事實 | 🟡 |
| `NEEDS_HUMAN` | 屬實質法律判斷（第 3、8 款） | 🟡 |

## 6. 模組規格

### 6.1 擷取層

- 輸入：訴願書 PDF、原處分 PDF
- 輸出：`CaseFacts`
- 實作：LLM 抽取，**強制 JSON schema**，每欄要求回傳 source
- 紅線：抽不到就回 `null`，**不准推測**

**⚠ 資料缺口**：資料集**沒有任何訴願書原件**，只有決定書。Demo 輸入需從決定書的「事實」＋「訴願意旨略謂」段反向合成，**簡報上必須明講**。

### 6.2 案件分類

- 規則優先：`要旨` 標頭 → 案件類型（實測 94/101）
- 備援：處分依據法規 → 類型映射
- **不需要訓練分類模型**

### 6.3 §77 判準引擎

八款各一個純函式，簽章統一：

```python
def gate_art77_para2(facts: CaseFacts, rules: RuleSet) -> GateResult: ...
```

**24 小時內的實作範圍**：

| 款 | Demo 範圍 |
|---|---|
| 第 2 款 | **完整實作 + 10 件測試** ← 高光 |
| 第 1、6、7 款 | 骨架 + 簡化條件 |
| 第 3、8 款 | 一律回 `NEEDS_HUMAN`（這是正確行為，不是偷懶） |
| 第 4、5 款 | 回 `NOT_APPLICABLE` 或 `NEEDS_HUMAN`，**簡報標示樣本不足無法驗證** |

### 6.4 期間計算模組

**這是全系統最該被獨立、最該有測試的一支。**

```
輸入：送達日、送達方式、收受機關、訴願人住居地、有無訴願代理人及其住居地
輸出：起算日、法定期間、在途期間、原末日、調整後末日、調整理由、是否逾期、逾期天數
```

規則來源（全部已從條文原文核對）：

| 規則 | 依據 |
|---|---|
| 次日起算 | 訴願法 §14 I、行政程序法 §48 II |
| 30 日 | 訴願法 §14 I |
| 以機關收受日為準 | 訴願法 §14 III |
| 誤向他機關 → 以該機關收受日為準 | 訴願法 §14 IV |
| 在途期間扣除（有代理人住居受理機關所在地者除外） | 訴願法 §16 I |
| 期間計算準用民法 | 訴願法 §17 |
| 末日為星期日／國定假日 → 次日；星期六 → 次星期一上午 | 行政程序法 §48 IV |
| 不利處分之末日「照計」的例外的例外 | 行政程序法 §48 V |
| 寄存送達生效日 | 行政程序法 §74 |

> ⚠ **行政程序法 §48 V 是雙重否定**：「期間涉及人民之處罰或其他不利行政處分者…其末日為星期日、國定假日或其他休息日者，**照計**。但依第二項、第四項規定計算，**對人民有利者，不在此限**。」訴願案的原處分幾乎都是裁罰（不利處分）會落進第 5 項，但「順延」通常對人民有利，於是又被但書拉回第 4 項。**這條必須寫成有測試的函式，任何語言模型在這裡都會擲骰子。**

### 6.5 法規版本／時效警示

> 🔴 **v0 的規則寫錯了法條，此處為修正版。**

行政罰法 §5 原文：

> 行為後法律或自治條例有變更者，適用**裁處時**之法律或自治條例。但**裁處前**之法律或自治條例有利於受處罰者，適用最有利於受處罰者之規定。

**從新從輕比較的是「行為時 → 裁處時」，訴願決定日不在比較區間內。** 原本設計的 `處分日 < 修正日 < 決定日` 在法律上是錯的。

拆成兩個不同觸發：

| | 觸發條件 | 依據 | 系統動作 |
|---|---|---|---|
| **A. 從新從輕** | 行為日 < 修正日 ≤ 處分日 | 行政罰法 §5 | 提示比較新舊法何者有利於受處罰者 |
| **B. 條次對照說明** | 處分日 < 修正日 < 決定日 | 決定書說理義務 | 提示交代條次變更、說明為何仍適用舊法 |

**兩者都必須先通過 §77 gate（確認進入實體審查）才觸發。** 程序不受理的案子根本不會涉及實體法適用。

**已知限制（實測）**：全資料集 71 件可判定案件中，B 規則觸發 8 件，其中 6 件是不受理案（缺 gate 造成的假陽性）。加上 gate 後剩 2 件，其中 1 件（113 年 #18 洗錢案）人工確認為真陽性——該決定書正文明文寫「違反修正前洗錢防制法第 15 條之 2 第 1 項（113 年 7 月 31 日條次變更為第 22 條第 1 項）」。**真實 precision / recall 在沒有法律專家標註前算不出來，簡報不得宣稱數字。**

**Demo 用例（情境 B）**：113 年 #18，處分日 113/7/13、洗錢防制法修正日 113/7/31、決定日 113/11/28。這是資料集裡唯一確認的真陽性。

### 6.6 稽核層

> **設計要求，不是後續優化——加在後面會很痛。**

稽核紀錄必須存 **規則版本雜湊**，不只存結論。否則規則改版後，「當初這案依什麼規則判的」就查不回來，稽核鏈失去意義。

```
AuditEntry {
  case_id, timestamp, actor(system|人名),
  gate_results: [...],          // 含每個 gate 的 rule_version
  ruleset_version: "sha256:...", // 整套規則的快照
  human_edits: [ {section, before, after, reason} ],
  prev_hash, entry_hash          // SHA-256 鏈
}
```
