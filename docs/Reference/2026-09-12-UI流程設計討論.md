# 會議記錄：訴願案 AI 輔助處理系統 — 使用者介面（UI，User Interface，也就是承辦人員實際會看到、點選操作的畫面）流程設計討論

- **日期**：2026-09-12
- **來源**：`大遠百.m4a`（錄音檔，長度約 25 分鐘；依內容判斷，有效討論集中在前 18 分 44 秒，之後是環境雜音，語音辨識模型對雜音誤判成文字雜訊，已略去不採用）
- **轉錄方式**：本機語音辨識模型 mlx-whisper（一款把語音轉成文字的辨識模型，直接在你自己電腦上跑、不會把錄音上傳到外部伺服器）+ 人工整理歸納。這不是逐字稿的照抄，而是把討論中反覆修正、插話、離題閒聊（例如中途聊到便當、路人問長官問題）濾掉後，按主題重新組織的結論。
- **出席者**：錄音中至少有 2～3 人交叉討論，但語音檔沒有標示身分，故本記錄不做發言者歸屬，只記錄「討論出的結論」與「還沒有共識的地方」。
- **本記錄性質**：這是團隊對著白板畫的架構圖（見下方〈對應白板〉一節），從「承辦人員第一天打開系統會怎麼用」的角度，把畫面流程重新推演一遍後的定案內容。**後續開發（尤其是 `frontend`）請以本記錄的畫面流程為準。**

## 一、對應白板架構圖

會議前拍的白板照片畫了一條從上到下的流程，這份記錄把白板上因為拍照角度被手擋住、看不清楚的字，用錄音內容補回來。對應關係如下：

1. 白板最上方的框（①②③ 編號列表 + 右上角上傳圖示）＝【畫面①：案件列表頁】。
2. 中間框（左右兩欄清單 + 右側「摘要／關鍵字」標註 + 「mock data」標註）＝【畫面②：案件內容頁】，「mock data」指的是官方比賽資料集裡沒有提供訴願書配對的行政處分書，這段要用假資料（mock data，開發時先用虛構樣本頂著跑，不是真的政府資料）示範。
3. 中間偏下、寫著「過」往下的框（勾選「法」「相關」兩個圈）＝【畫面⑤：法條與相關案例勾選頁】。
4. 右側寫著「不過」的框（草稿 + 一排 ✓/✗）＝【畫面④：不受理草稿頁】。
5. 最下方框（草稿 + 可編輯/下載圖示 + 迴圈圖示）＝【畫面⑥：正式決定書草稿頁】。

## 二、畫面流程逐項說明

### 畫面①：案件列表頁（進系統看到的第一頁）— 對應錄音 00:08–01:00

- 承辦人員一進系統，最想看到的就是「手上有哪些訴願案件」，所以第一頁是**案件列表**，每筆案件顯示類似「訴願書 1」「訴願書 2」的樣式。
- 列表要區分「處理中／處理到一半」跟「未處理」的狀態，因為同一個人可能同時開著好幾個案件、這個處理一半又跑去開下一個。
- 右上角有一個**上傳按鈕**，讓承辦人員自己把新拿到的訴願書拖上來、加進列表——**檔案是承辦人員自己選要處理哪些才上傳，不是系統把所有檔案一次全部列出來**（討論中特別排除了「所有檔案都攤在網頁上」這個做法，理由是那樣網頁會很亂）。

### 畫面②：案件內容頁（點進某一筆案件之後）— 對應錄音 03:19–08:40

- 點進去先看到這份訴願書的原文內容。
- 旁邊會有一欄**摘要**（AI 自動生成的重點整理）和**關�键字**——之所以要保留關鍵字，是因為討論中假設承辦人員原本的工作習慣就是先看關鍵字抓重點，系統應該延續這個習慣，而不是強迫他們改用一套新方式。
- **重要發現與決策**：訴願書裡由申請人自己填寫的「事實欄」通常寫得很短、很口語（例如「我被判闖紅燈，但我覺得是黃燈」），因為申請人是一般民眾，不是在寫法律文件。光靠這段文字做摘要資訊量不夠。
  - 討論釐清了「事實欄」跟「理由欄」的差異：**事實欄**是原本裁罰機關（例如警察）認定的事實（「你闖紅燈」）；**理由欄**才是申請人自己的主張（「我覺得沒有」）。
  - 關鍵結論：裁罰機關寄給申請人的**行政處分書**（原始的裁罰通知，內容遠比訴願書裡簡短帶過的事實欄詳細）才是做摘要時真正該參考的完整資訊來源。
  - 但官方提供的比賽資料集裡**沒有**「同一案件」的訴願書＋行政處分書配對資料，所以這段功能開發時得先用 mock data（假資料）示範這個配對關係怎麼運作，正式資料之後再補。
- 下一步按鈕會觸發「分析第 77 條」。

### 畫面③：第 77 條分析結果頁（過 / 不過分流）— 對應錄音 09:10–09:45

- 「第 77 條」指的是訴願法第 77 條的 8 款程序性駁回事由（也就是 `docs/開發文件.md` 裡已經記載的「排除性確認」判準——這 8 款裡第 3、8 款需要人工判斷，其餘可以規則化檢核，這點跟會議結論一致）。
- 系統跑完這個檢查後，畫面上直接顯示**過**或**不過**兩種結果，往下走不同分支。

### 畫面④（不過分支）：不受理草稿頁 — 對應錄音 09:45–10:25

- 一旦判定「不過」，系統**直接產生一份草稿**，說明是第 77 條哪一款不符合。
- 旁邊要列出全部 8 款，用打勾／打叉標示哪幾款符合、哪幾款不符合。
- **這個打勾/打叉不是 AI 的主觀判斷，是規則化的格式檢核**（討論原話：「這不是 AI 判斷，因為他是一個格式設定」）——這點跟專案既有設計（`docs/開發文件.md` 裡第 3、8 款才需要轉人工，其餘走規則）是吻合的。
- 這份草稿**一定要可編輯、可下載**，這是明確要求，不能只是唯讀畫面。

### 畫面⑤（過分支）：法條與相關案例頁 — 對應錄音 10:25–14:55

- 判定「過」（程序上受理）之後，**不做事實查核**——這是本次會議最重要的範圍界定之一。理由是：訴願制度審的是「這個人被裁罰的行為，跟裁罰時引用的法條之間，適用關不關聯得起來」，不是重新調查「這個人到底有沒有做這件事」；既然拿到的資料本來就已經預設事實成立，系統就不需要、也不應該去做事實查核。
- 這一頁要顯示：**相關法條**＋**相關案例**（過去引用同一法條的訴願案例，分成「正方」——申請人成功、處分被撤銷；跟「反方」——申請人失敗、訴願被駁回）。
- 順序上決定**先法條、後案例**：因為訴願書裡本來就會寫出「被依哪一條裁罰」，系統可以直接先推薦對應法條，再拿這條法條過去的正反案例給承辦人員參考，而不是反過來。
- 這頁承辦人員可以**勾選**要引用哪些法條、哪些案例（對應白板中間框「勾選」「法」「相關」的標註），勾完才進到下一步的草稿生成。

### 畫面⑥：正式決定書草稿頁 — 對應錄音 14:55–16:50、18:20（討論中斷處）

- 草稿頁**同樣要求可編輯、可下載**——這個要求在「不過」分支和「過」分支都重複強調，是硬性條件。
- 討論結尾提到「這裡一定會用到 LLM（大型語言模型，Large Language Model，也就是像 Gemini／ChatGPT 這類負責生出草稿文字內容的 AI 模型）」，語氣是肯定會需要，但錄音在講到「放在哪個環節」時被截斷，**沒有錄到具體結論**，這點列入下方待釐清事項。

## 三、明確決定「不做」的事

- **不做事實查核**：系統假設訴願書/ 行政處分書裡陳述的事實為真，只比對「行為」與「所引用法條」是否相符，不重新調查案件真相。這和 `docs/開發文件.md` 裡對訴願制度審查範圍的既有理解一致，會議只是把它明確落實到 UI 流程上。
- **不把所有檔案一次攤在網頁上**：上傳與列表都是承辦人員主動選擇要處理的案件，不是系統批次匯入全部檔案。

## 四、資料缺口與因應（對應白板「mock data」標註）

- 官方資料集**沒有**同一案件的「訴願書＋行政處分書」配對資料，也拿不到真實申請人送出的訴願書全文（不會公開，牽涉隱私）。
- 行政處分書本身是可公開查到的，但無法確認某一份行政處分書「有沒有」被提起訴願、對應到哪一份訴願書。
- **結論**：demo（展示用原型）階段先用假資料模擬這組配對關係，不影響整體流程驗證。

## 五、待釐清事項（下次會議或開發時需要再確認）

1. **LLM（大型語言模型）具體要放在流程的哪個環節**——錄音在討論到這裡被截斷，只確認「一定會用到」，沒有錄到是用在摘要、草稿理由段，還是其他地方（依現有 `src/draft.py` 設計，理由欄本來就是 LLM 生成的三段論，這點應可延續，但需要跟今天的結論對一次）。
2. 案件列表頁「處理中」狀態的判定規則（存檔草稿？還是只要開過就算？）討論中沒有給出明確定義。
3. 畫面②的「摘要＋關鍵字」用行政處分書 mock data 產生後，正式串接真實資料的時間點與資料來源，需要再確認。

## 六、建議下一步（銜接現有程式碼）

對照 `frontend`（現役 Vue 3 前端）與 `src/` pipeline 既有四階段（intake → recommend → similar → draft），這次會議等於把畫面流程釘死了，可以直接對應規劃頁面元件：

- 畫面①②：目前前端若還沒有案件列表 / 上傳頁，這是第一個要補的頁面，串 `src/intake.py` 的 `parse_incoming_pdf()`。
- 畫面③④：串 `Stage2Recommender` 裡第 77 條的排除性確認邏輯（若尚未拆出獨立的「過/不過」API 回傳格式，需要先補這個欄位）。
- 畫面⑤：串 `Stage2Recommender`（法條推薦）+ `Stage3SimilarCases`（相似案例，含正反方），並在前端加上勾選狀態的資料流。
- 畫面⑥：串 `src/draft.py` 的 `build_draft()`，前端要能編輯回傳內容並觸發 `docx_export.py` 下載。

這份文件目的是把方向定下來，實際頁面元件與 API 串接沒有在這次會議討論範圍內，需要另外規劃再動手。
