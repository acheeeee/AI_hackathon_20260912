# 分工、實作順序與驗收

日期：2026-09-12｜v1.0｜設計為文件交付；實作進度見 §6，下表逐案標註狀態

## 1. 分工邊界

| 負責人 | 本次工作 |
|---|---|
| 前端／design 同事 | 主畫面直接編輯、註記、selection target、側邊欄、來源卡、diff／衝突畫面、版本提示與 API client |
| 資料同事 | 前處理 release、來源 spans、合法原文、版本／時效資訊、標註與評估資料；對接來源查詢介面 |
| 後端／你 | 案件隔離、SQLite、API、版本／失效、規則試算、人工覆核與分流、交易採用、稽核及部署 |
| AI 實作負責人（可由你兼任） | 協調器、intent、context、工具、來源查證、patch／完整候選、串流與評估 |
| 驗收／法律覆核負責人 | 逐案確認法律規則與 gold，檢查人工覆核與未決事項，不把設計圖當答案 |

前端與資料已有人進行，不等於 API／AI 協調器已有負責人。任一未指派角色由你在團隊內落實；本文件未對任何人發送訊息或自動派工。

## 2. 實作順序

### 階段 A：共同範例與最小狀態

先完成 case ID、SQLite migration、事實／草稿版本、TargetRef／Proposal／EvidenceRef schemas 與 API fixtures。以前端假回應展示兩條流程：「直接修改欄位」與「選一句話→AI 候選→採用」。

交付：真實可讀寫的案件 API、衝突回應、前端可選取／加註／顯示 diff；AI 暫用固定合成候選。驗收要證明兩案不混、重整保留、未採用不改正文。

### 階段 B：先做 AI 解釋與查證

接本地 read/search/open 工具與真實活動事件，完成來源卡、規則 trace 解釋及缺證回覆。資料全庫尚未交付時用已核對的小批次，不需要等全庫向量化。

交付：對選取範圍回答、列實際開啟資料、無來源明示；還不能改正式內容。工具事件必須與實際執行一致。

### 階段 C：局部修改與事實更正

接 patch verifier、修改組、三方預覽與 transaction apply。先完成純文字潤飾，再接事實更正→試算→採用→重算及人工覆核。

交付：一條可用的局部編修鏈；重複提交不重複寫入，對方已改同一句時正確顯示 conflict。

### 階段 D：完整重生與版本回復

接完整候選、保留人工段落、分組採用、依賴過期、撤回及送審快照。重新生成使用與局部編修同一套提案機制。

交付：更新事實後完整重生，人工內容與舊稿都能查；局部採用不會錯誤解除整份 stale。

### 階段 E：整合、模型失敗與展示

跑三條案件分流、多案並行、斷網／取消／重啟恢復、DOCX 與來源回查。記錄模型延遲及用量；最後才按 dev 結果調 token／工具預算，不在 holdout 調參。

## 3. 可執行的驗收案例清單

| ID | 操作／情境 | 必須觀察到的結果 | 狀態 |
|---|---|---|---|
| H01 | 人工修改已擷取日期 | 原值可查、新事實版本、相關分析 stale／重算 | PASS＊ |
| H02 | 對日期加疑問註記但不採用修改 | 註記保存，正式日期不變 | PASS |
| H03 | 人工覆核待確認款別 | 系統原結果保留，人工結果與理由並列，分流重算 | NOT RUN |
| H04 | 否定唯一觸發款，其他款仍待確認 | 停在 human_review，不直接進實體推薦 | NOT RUN |
| H05 | 前導頁手改逾期天數 | 進入試算／個案覆核流程，不只改顯示文字 | NOT RUN |
| A01 | 選取同文句第二次出現處再改寫 | 只改正確 block／range | NOT RUN |
| A02 | 局部改寫改到未選取段落 | OUT_OF_SCOPE_PATCH；正文不變 | PASS |

| V03 | 選取文字沒變但相關事實改了 | DEPENDENCY_STALE，不能只驗文字 hash | PASS |
| V04 | 完整重生含人工修改 | base／current／candidate 可比，未採用前 current 不變 | PASS |
| V05 | 採用一組文字但不採必要引用 | 拒絕不完整依賴組 | PASS |
| V06 | 採用成功但回應丟失，重送 | 同一結果版本，不新增第二次修改 | PASS |
| V07 | DB 保存中斷 | 文件／case head／audit 同時成功或同時不變 | PASS |
| V08 | 兩案交錯聊天、生成、下載 | 全程 case ID 與來源一致 | NOT RUN |
| V09 | 撤回舊修改時已有後續編輯 | 顯示新 diff，不吞掉後續工作 | NOT RUN |
| V10 | 已送審後再編輯 | 新工作版本，舊 submission 快照不變 | NOT RUN |
| S01 | SSE 斷線重連 | 按 sequence 補送，不重跑模型／重套提案 | PASS＊ |
| S02 | run 取消後再回傳供應商結果 | 不產生可採用的新提案，不改正文 | PASS＊ |
| S03 | 服務重啟與備份還原 | 已採用版本、稽核及來源可回查 | NOT RUN |

A02、V01、V02 的候選仍是由 fixture 端點建立的合成提案，不是真的模型 run。B3 的 fixed-provider 端到端測試另外證明 A03（search 3／open 1）、A04（快照缺口）、A08、S01 與 S02 的限定版本。

＊A08 目前驗證「provider 拋錯→run/job failed、錯誤不洩漏輸入、人工草稿端點仍可寫入」；未另測 rate limit 與 timeout。S01 驗證已完成 run 依 Last-Event-ID 補送、事件數不增；目前是有限 SSE replay，尚無等待新事件的長連線。＊S02 修掉一個真的競態：run 被取消後，若供應商仍在同一個背景工作裡把結果寫回，`complete_run` 會因為狀態已非 `running` 而丟出例外；原本的例外處理會呼叫 `fail_run` 再丟一次同樣的例外，未被接住並穿出背景工作。修法是讓 `fail_run` 對已是終態的 run 直接視為無動作，測試模擬供應商在 `execute()` 內部呼叫 `cancel_run` 來重現這個時序，驗證 run 停在 `cancelled`、不產生 `run.completed`、也不保存 assistant 訊息。這只證明單一背景工作內的順序競態，不是多行程／多副本情境下的競態，S03 的伺服器重啟仍待驗證。

＊H01 只通過到「原值可查、新事實版本、草稿標 stale、人工覆核後才恢復 current」。規則引擎尚未實作，所以「相關分析 stale／重算」這一半仍是 NOT RUN；目前的失效標記是保守作法，任何事實變動都把草稿標過期，不宣稱已能精確判斷影響範圍。

所有日期／法律案例另由已核對規則測試提供；上表主要驗證系統行為，不表示已證明法律判斷正確。

## 4. 需要一併決定但不阻擋原型的部署事項

- 誰能覆核、誰能內部送審：v1 先由具案件編輯權的承辦人操作並保存身分；實際組織權限之後接入，不用匿名 actor 冒充正式稽核。
- 是否允許外部官方來源／雲端模型：按部署已批准能力提供，未接入則本地快照與明確缺口。
- 送陳核是否連正式系統：本次只建內部快照，外部公文連接另定契約。
- 模型與編輯器選型：不在此綁死插件或新套件；先以現有 Vue／Provider 建立契約驗證，再確認新增依賴。

## 5. 交付完成定義

前端能操作、API 真正保存、AI 顯示真實來源、候選未採用不寫入、局部／全文都能 diff 採用、人工修改可恢復、多案不混、正式變更有稽核。交付報告列測例結果、已知限制、模型／prompt／KB／規則版本與未完成項。

本套規格的 A1 至 A3、B0 證據底座、B1 run／事件、B2 Evidence 工具、B3 固定模型端到端與線上 AgentCore provider 已實作；B 後續（proposal 生成 intent）與 C 至 E 尚未完成。上表狀態只按端到端實跑證據更新；A06 等未測試情境維持 NOT RUN。

已知偏離與缺口：

- **`POST /api/v1/cases/{case_id}/drafts` 是階段 A 暫時入口。** 已回寫 04 契約，正式流程仍應由抽文／生成建立；現階段保留以驗證編輯與 diff。
- **身分是單人 stub session。** actor 由伺服器設定固定，前端不能指定。跨案隔離的測試因此只驗同一 actor 下的不同案件，多人權限尚未驗證。
- **`gate_result` 與 `source_span` 兩種 TargetRef 只驗形狀。** 還沒有 analyses 與來源快照表，所以不驗目標是否真的存在。
- **`POST /api/v1/cases/{case_id}/proposals` 是階段 A fixture 入口。** 已回寫 04 契約；接真 run 後應限測試用或移除，不能把呼叫端提供的內容當正式 AI 證據。
- **查證寫入路徑已由 fixed run 與 agentcore run 實際使用，但尚無模型提案鏈。** `verify` 可將 r3 search／open、program-verified evidence 與 assistant answer 串成同一 run；`support_status` 仍為 `unknown`。現有階段 A 合成提案端點若自帶 evidence，仍保存 null／`unverified`。兩個 provider 都不產生 proposal，不改正式內容。
- **同一區塊的字元級自動合併沒做。** 依設計 03 §6.1 規則 3 保守視為衝突，交人工整合。完整文件的衝突也是整份判定，不做逐段自動合併。
- **沒有勾選依據端點（`PATCH /selections`）。** 引用是否齊備只靠修改組之間的依賴閉包把關。
- **fixed 聊天與有限 SSE replay 已有，但還不是生產 worker。** Starlette background task 在單機 demo 能完成 run，服務中止時不保證恢復；SSE 回傳已保存快照後關閉，不等待新事件。proposal 產生、分析與送審仍未接；線上 provider 已接（見 07）。
