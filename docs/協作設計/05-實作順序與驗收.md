## 2. 實作順序

### 階段 A：共同範例與最小狀態

先完成 case ID、SQLite migration、事實／草稿版本、TargetRef／Proposal／EvidenceRef schemas 與 API fixtures。以前端假回應展示兩條流程：「直接修改欄位」與「選一句話→AI 候選→採用」。

交付：真實可讀寫的案件 API、衝突回應、前端可選取／加註／顯示 diff；AI 暫用固定合成候選。驗收要證明兩案不混、重整保留、未採用不改正文。

### 階段 B：先做 AI 解釋與查證

接本地 read/search/open 工具與真實活動事件，完成來源卡、規則 trace 解釋及缺證回覆。資料全庫尚未交付時用已核對的小批次，不需要等全庫向量化。

交付：對選取範圍回答、列實際開啟資料、無來源明示；還不能改正式內容。工具事件必須與實際執行一致。

### 階段 C：局部修改與事實更正

接 patch verifier、修改組、三方預覽與 transaction apply。先完成純文字潤飾，再接事實更正→試算→採用→重算及人工覆核。

交付：一條可用的局部編修鏈；重複提交不重複寫入，對方已改同一句時正確顯示 conflict。

### 階段 D：完整重生與版本回復

接完整候選、保留人工段落、分組採用、依賴過期、撤回及送審快照。重新生成使用與局部編修同一套提案機制。

交付：更新事實後完整重生，人工內容與舊稿都能查；局部採用不會錯誤解除整份 stale。

### 階段 E：整合、模型失敗與展示

跑三條案件分流、多案並行、斷網／取消／重啟恢復、DOCX 與來源回查。記錄模型延遲及用量；最後才按 dev 結果調 token／工具預算，不在 holdout 調參。

2026-09-13 的草稿生成（`draft` intent）雖然讓提案第一次真的由模型 run 產生，上表**沒有任何一列因此改狀態**，理由要說清楚：`draft` 產生的是單一 `mode=full`、單一修改組的完整候選，沒有逐段局部候選，所以 A01／A02（選取範圍越界）與 V01／V02（同段落三方衝突）的情境仍然只有 fixture 提案測過；A05（新法律主張引用未勾選資料）要有「文字改動」與「引用改動」兩個可分開採用的修改組才測得出來，現在只有一組，沒有可以只採用一半的情況；A06（來源只部分支持或互相衝突）需要判斷支持程度，而 `support_status` 仍是 `unknown`；A07（PDF 內含指令要求改別案）沒有做過注入測試。這些維持 NOT RUN。

＊A08 目前驗證「provider 拋錯→run/job failed、錯誤不洩漏輸入、人工草稿端點仍可寫入」；未另測 rate limit 與 timeout。S01 驗證已完成 run 依 Last-Event-ID 補送、事件數不增；目前是有限 SSE replay，尚無等待新事件的長連線。＊S02 修掉一個真的競態：run 被取消後，若供應商仍在同一個背景工作裡把結果寫回，`complete_run` 會因為狀態已非 `running` 而丟出例外；原本的例外處理會呼叫 `fail_run` 再丟一次同樣的例外，未被接住並穿出背景工作。修法是讓 `fail_run` 對已是終態的 run 直接視為無動作，測試模擬供應商在 `execute()` 內部呼叫 `cancel_run` 來重現這個時序，驗證 run 停在 `cancelled`、不產生 `run.completed`、也不保存 assistant 訊息。這只證明單一背景工作內的順序競態，不是多行程／多副本情境下的競態，S03 的伺服器重啟仍待驗證。

＊H01 只通過到「原值可查、新事實版本、草稿標 stale、人工覆核後才恢復 current」。規則引擎尚未實作，所以「相關分析 stale／重算」這一半仍是 NOT RUN；目前的失效標記是保守作法，任何事實變動都把草稿標過期，不宣稱已能精確判斷影響範圍。

所有日期／法律案例另由已核對規則測試提供；上表主要驗證系統行為，不表示已證明法律判斷正確。

已知偏離與缺口：

- **`POST /api/v1/cases/{case_id}/drafts` 已退場為測試 fixture。** OpenAPI 標 `deprecated`，前端不再呼叫；正式流程走 `POST /cases/{id}/draft-generations`。保留它是因為版本／合併的驗收測試要靠它建初始草稿。
- **身分是單人 stub session。** actor 由伺服器設定固定，前端不能指定。跨案隔離的測試因此只驗同一 actor 下的不同案件，多人權限尚未驗證。
- **`gate_result` 與 `source_span` 兩種 TargetRef 只驗形狀。** 還沒有 analyses 與來源快照表，所以不驗目標是否真的存在。
- **`POST /api/v1/cases/{case_id}/proposals` 已退場為測試 fixture。** OpenAPI 標 `deprecated`，只剩 merge／apply 測試在用；真提案由 `draft` intent 的 run 產生，呼叫端自帶的 evidence 仍一律存成 `unverified`。
- **模型提案鏈已接上，但只到「產生提案」為止。** `draft` intent 把選定法規逐條 `open_source`，用 program-verified evidence 當修改組的 `evidence_ids` 產生 `replace_document` 提案；`support_status` 仍是 `unknown`——開啟原文只證明來源存在且引文一致，不代表那一條支持本案結論。提案的採用（merge preview → application）目前只有 API 與測試，**前端沒有採用／編輯畫面**，所以生成的草稿還進不了正文。
- **AgentCore 草稿現有兩層安全閘門，但不是法律正確性證明。** 遠端草稿只收到固定、呼叫端不可覆寫的任務 prompt：訴願書節錄只能視為當事人主張，忽略 context 內嵌指令，不得補機關／事實或寫最終決定；模型回傳後，本機再以決定主文、受理機關、駁回／不受理／有無理由／撤銷或維持原處分等標記做整段阻擋，安全輸出則一律標成「AI 建議理由（未經法律覆核）」。這個字串閘門只擋已知高風險類型，**不等於一般幻覺偵測，也不判斷法律分析是否正確**；修補後 AgentCore 真實重測因敏感內容外送未獲明確授權而維持 NOT RUN。
- **同一區塊的字元級自動合併沒做。** 依設計 03 §6.1 規則 3 保守視為衝突，交人工整合。完整文件的衝突也是整份判定，不做逐段自動合併。
- **沒有勾選依據端點（`PATCH /selections`）。** 引用是否齊備只靠修改組之間的依賴閉包把關。
- **fixed 聊天與有限 SSE replay 已有，但還不是生產 worker。** Starlette background task 在單機 demo 能完成 run，服務中止時不保證恢復；SSE 回傳已保存快照後關閉，不等待新事件。proposal 產生、分析與送審仍未接；線上 provider 已接（見 07）。
