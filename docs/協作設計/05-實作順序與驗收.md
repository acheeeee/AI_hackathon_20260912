## 2. 實作順序

### 階段 A：共同範例與最小狀態

先完成 case ID、SQLite migration、事實／草稿版本、TargetRef／Proposal／EvidenceRef schemas 與 API fixtures。以前端假回應展示兩條流程：「直接修改欄位」與「選一句話→AI 候選→採用」。

交付：真實可讀寫的案件 API、衝突回應、前端可選取／加註／顯示 diff；AI 暫用固定合成候選。驗收要證明兩案不混、重整保留、未採用不改正文。

### 階段 B：先做 AI 解釋與查證

接本地 read/search/open 工具與真實活動事件，完成來源卡、規則 trace 解釋及缺證回覆。資料全庫尚未交付時用已核對的小批次，不需要等全庫向量化。

交付：對選取範圍回答、列實際開啟資料、無來源明示；還不能改正式內容。工具事件必須與實際執行一致。

### 階段 C：局部修改與事實更正

接 patch verifier、修改組、三方預覽與 transaction apply。先完成純文字潤飾，再接事實更正→試算→採用→重算及人工覆核。

交付：一條可用的局部編修鏈；重複提交不重複寫入，對方已改同一句時正確顯示 conflict。

### 階段 D：完整重生與版本回復

接完整候選、保留人工段落、分組採用、依賴過期、撤回及送審快照。重新生成使用與局部編修同一套提案機制。

交付：更新事實後完整重生，人工內容與舊稿都能查；局部採用不會錯誤解除整份 stale。

### 階段 E：整合、模型失敗與展示

跑三條案件分流、多案並行、斷網／取消／重啟恢復、DOCX 與來源回查。記錄模型延遲及用量；最後才按 dev 結果調 token／工具預算，不在 holdout 調參。

V01、V02 的候選仍是由 fixture 端點建立的合成提案，不是真的模型 run。B3 的 fixed-provider 端到端測試另外證明 A03（search 3／open 1）、A04（快照缺口）、A08、S01 與 S02 的限定版本。

2026-09-13 §7.3 完成後，A01 已由真的 `revise_selection` intent 端到端測試證明（`backend/tests/test_revise_selection.py::test_revise_selection_scopes_a_local_proposal_to_the_second_occurrence`）：同一詞組在區塊裡出現兩次，`target` 精準指向第二次出現，跑完整個 chat run 後，提案的 `replace_text` 操作範圍精準等於第二次出現的字元範圍，且草稿正文在提案未採用前完全不變。A02（局部改寫改到未選取段落）的一般性保護仍由 `test_proposals_api.py` 的 fixture 提案驗證；`revise_selection` 的設計讓提案的頂層 `target` 與操作自己的 `target` 永遠是同一個 `DraftBlockTarget`（見 `caseapi/services/revise_selection_service.py`），模型沒有管道指定不同範圍，所以沒有另外重造一個「模型試圖越界」的 A02 情境——這是架構上排除該風險，不是沒測。

2026-09-13（草稿生成當批）的 `draft` intent 雖然讓提案第一次真的由模型 run 產生，上表當時**沒有任何一列因此改狀態**：`draft` 產生的是單一 `mode=full`、單一修改組的完整候選，沒有逐段局部候選，所以 A01／A02（選取範圍越界）與 V01／V02（同段落三方衝突）的情境當時仍然只有 fixture 提案測過。A01 已在同一天稍後由 §7.3 的 `revise_selection` intent 補上真實測試（見上一段）；V01／V02（同段落三方衝突）仍然只有 fixture 提案測過，因為目前還沒有能產生「同一草稿的兩個並行候選」的 run 情境。A05（新法律主張引用未勾選資料）要有「文字改動」與「引用改動」兩個可分開採用的修改組才測得出來，現在只有一組，沒有可以只採用一半的情況；A06（來源只部分支持或互相衝突）需要判斷支持程度，而 `support_status` 仍是 `unknown`；A07（PDF 內含指令要求改別案）沒有做過注入測試。這些維持 NOT RUN。

＊A08 目前驗證「provider 拋錯→run/job failed、錯誤不洩漏輸入、人工草稿端點仍可寫入」；未另測 rate limit 與 timeout。S01 驗證已完成 run 依 Last-Event-ID 補送、事件數不增；目前是有限 SSE replay，尚無等待新事件的長連線。＊S02 修掉一個真的競態：run 被取消後，若供應商仍在同一個背景工作裡把結果寫回，`complete_run` 會因為狀態已非 `running` 而丟出例外；原本的例外處理會呼叫 `fail_run` 再丟一次同樣的例外，未被接住並穿出背景工作。修法是讓 `fail_run` 對已是終態的 run 直接視為無動作，測試模擬供應商在 `execute()` 內部呼叫 `cancel_run` 來重現這個時序，驗證 run 停在 `cancelled`、不產生 `run.completed`、也不保存 assistant 訊息。這只證明單一背景工作內的順序競態，不是多行程／多副本情境下的競態，S03 的伺服器重啟仍待驗證。

＊H01 只通過到「原值可查、新事實版本、草稿標 stale、人工覆核後才恢復 current」。規則引擎尚未實作，所以「相關分析 stale／重算」這一半仍是 NOT RUN；目前的失效標記是保守作法，任何事實變動都把草稿標過期，不宣稱已能精確判斷影響範圍。

所有日期／法律案例另由已核對規則測試提供；上表主要驗證系統行為，不表示已證明法律判斷正確。

## 4. 需要一併決定但不阻擋原型的部署事項

- 誰能覆核、誰能內部送審：v1 先由具案件編輯權的承辦人操作並保存身分；實際組織權限之後接入，不用匿名 actor 冒充正式稽核。
- 是否允許外部官方來源／雲端模型：按部署已批准能力提供，未接入則本地快照與明確缺口。
- 送陳核是否連正式系統：本次只建內部快照，外部公文連接另定契約。
- 模型與編輯器選型：不在此綁死插件或新套件；先以現有 Vue／Provider 建立契約驗證，再確認新增依賴。

已知偏離與缺口：

- **`POST /api/v1/cases/{case_id}/drafts` 已退場為測試 fixture。** OpenAPI 標 `deprecated`，前端不再呼叫；正式流程走 `POST /cases/{id}/draft-generations`。保留它是因為版本／合併的驗收測試要靠它建初始草稿。
- **身分是單人 stub session。** actor 由伺服器設定固定，前端不能指定。跨案隔離的測試因此只驗同一 actor 下的不同案件，多人權限尚未驗證。
- **`gate_result` 與 `source_span` 兩種 TargetRef 只驗形狀。** 還沒有 analyses 與來源快照表，所以不驗目標是否真的存在。
- **`POST /api/v1/cases/{case_id}/proposals` 已退場為測試 fixture。** OpenAPI 標 `deprecated`，只剩 merge／apply 測試在用；真提案由 `draft` intent 的 run 產生，呼叫端自帶的 evidence 仍一律存成 `unverified`。
- **完整草稿提案與局部 AI 修改都已接上採用／拒絕，完整文件的人工整合 UI 仍沒有。** `draft` intent 把選定法規逐條 `open_source`，用 program-verified evidence 當修改組的 `evidence_ids` 產生 `replace_document` 提案；`revise_selection` intent（2026-09-13）用同一套 `proposal_service` 產生 `mode=local`／`replace_text` 提案，範圍鎖死在使用者選取的 `DraftBlockTarget`。前端對兩者都先做 merge preview，再由人工按鈕 application 或 rejection；正文區塊也可用既有 PATCH 逐段保存。`support_status` 仍是 `unknown`——開啟原文只證明來源存在且引文一致，不代表那一條支持本案結論；完整文件衝突只阻擋並提示，尚未接 `resolutions` 的人工整合 UI。
- **AgentCore 草稿現有兩層安全閘門，但不是法律正確性證明。** 遠端草稿只收到固定、呼叫端不可覆寫的任務 prompt：訴願書節錄只能視為當事人主張，忽略 context 內嵌指令，不得補機關／事實或寫最終決定；模型回傳後，本機再以決定主文、受理機關、駁回／不受理／有無理由／撤銷或維持原處分等標記做整段阻擋，安全輸出則一律標成「AI 建議理由（未經法律覆核）」。這個字串閘門只擋已知高風險類型，**不等於一般幻覺偵測，也不判斷法律分析是否正確**；修補後 AgentCore 真實重測因敏感內容外送未獲明確授權而維持 NOT RUN。`revise_selection`（2026-09-13）共用同一份危險字樣清單（抽成 `draft_composition.unsafe_reasoning_markers`），命中就整段換成阻擋訊息、不寫入提案；候選文字本身不套用「AI 建議理由」那個標籤前綴，因為候選會直接變成草稿正文，不該混進 UI 用語。
- **同一區塊的字元級自動合併沒做。** 依設計 03 §6.1 規則 3 保守視為衝突，交人工整合。完整文件的衝突也是整份判定，不做逐段自動合併。
- **沒有勾選依據端點（`PATCH /selections`）。** 引用是否齊備只靠修改組之間的依賴閉包把關。
- **fixed 聊天與有限 SSE replay 已有，但還不是生產 worker。** Starlette background task 在單機 demo 能完成 run，服務中止時不保證恢復；SSE 回傳已保存快照後關閉，不等待新事件。proposal 產生、分析與送審仍未接；線上 provider 已接（見 07）。
