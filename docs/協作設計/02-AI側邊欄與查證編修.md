# AI 側邊欄、來源查證與局部編修設計

日期：2026-09-12｜v1.0 設計｜B0 證據讀取／BM25 已實作；run、工具活動與側邊欄尚未實作

## 1. AI 的工作契約

AI 是在案件工作文件旁的協作助手。它能讀取被選取的內容、解釋規則計算、查詢資料、提出內容調整，並讓使用者看到它實際讀了哪些材料。AI 對話不自動成為事實、人工覆核或已採用文件。

輸出分為 `answer`（答覆）、`evidence`（可開啟來源）、`proposal`（尚未套用的修改）、`activity`（實際工具活動）四種。可以在同一回合出現多種，但狀態要明確：**「已提出」與「已套用」不能混用。**

資料來源、工具能力與版本均由後端提供；AI 不自行宣告已查資料，也不能直接執行 SQL、改 SQLite、呼叫正式套用或送審端點。

## 2. 五種主要意圖

| `intent` | 使用者例句 | AI 行為 | 正式內容是否改變 |
|---|---|---|---|
| `explain` | 「為什麼這邊算成這樣？」 | 讀選取內容、對應計算紀錄、來源並作可核對說明 | 否 |
| `verify` | 「請查這條法規是否適用這個說法」 | 釐清命題、查找／開啟原文、比較依據與缺口 | 否；可附修改建議 |
| `revise_selection` | 「把這一句寫得更正式」 | 只對指定工作範圍提出 replacement 與 diff | 採用後才改 |
| `regenerate_document` | 「用更新後資料完整重生這份草稿」 | 以指定版本的事實、人工決策、勾選依據建立完整候選 | 採用後才改 |
| `discuss` | 「我認為這個日期不是送達日」 | 辨別這是疑問、假設或欲更正事實；回覆或提出有明確目標的提案 | 只在採用提案／人工儲存時改 |

加註記、手動編輯、人工覆核由 UI 直接呼叫案件 API，不強制經過模型。前端可預填 intent，伺服器仍要檢查 intent 與範圍是否相容。聊天要求「全部改掉」但沒有指定文件時，回 `needs_input` 並要求定位。

### AI 怎麼解釋判斷

說明固定包含「使用的輸入」「適用的規則版本」「可驗算步驟」「引用原文」「仍待確認之處」。期間天數直接引用規則引擎的結構化結果；不能用模型重新心算再冒充引擎結果。

顯示的是供使用者核對的理由與工具紀錄，不要求揭露模型內部逐步思考。沒有計算紀錄就先調用試算工具，否則明說尚未取得；不能補出一段看似合理的歷史執行過程。

## 3. 選取範圍與上下文

### 3.1 支援的目標

- `draft_block`：可編輯工作文件的區塊及文字範圍。
- `fact_field`：案件事實 path，例如 `service.date`。
- `gate_result`：檢核 ID、分析版本與請求範圍。
- `source_span`：PDF／知識庫不可變來源。
- `annotation`：某筆註記版本。
- `document`：完整重生的指定工作文件。

每個目標帶 `case_id`、資源 ID、`resource_revision`。文字選取加 `block_id`、0 起算的 code point 範圍、`selected_text`、`selected_text_sha256` 與前後短文。前後短文只協助重新定位，不能替代版本／hash 核對。

原文來源沿用[前處理規格](../資料前處理與切分交接規格.md)的 `document_id/extraction_version/page/line/char_start/char_end`。工作草稿的 `block_id` 不等於知識庫 `chunk_id`，兩者必須分欄。

使用者選取兩處不連續文字，v1 要求分開提出修改或明確給出兩個 target；不以最前到最後位置一刀覆蓋中間未選內容。

### 3.2 上下文裝配順序

1. 使用者本次要求、intent、目標與範圍。
2. 該資源的已儲存版本及必要相鄰段落。
3. 相關已確認事實、系統結果、有效人工覆核、勾選依據快照。
4. 使用者指定的註記與本對話相關訊息；註記保留 `human_asserted/unverified` 語意。
5. 檢索並真正開啟的來源片段；每個片段帶來源 ID、版本與時效狀態。

聊天記憶只是討論脈絡。與目前案件事實不同時，以目前版本為準並提示差異；不能把聊天中的「假設日期為……」當成已儲存日期。跨案件引用需另行明確授權且有權限，v1 預設不提供跨案聊天搜尋。

每個 run 保存 `context_manifest`：讀取的資源版本、目標 hash、證據 ID、`kb_release_id`、規則版本、提示詞版本、模型識別與省略項目。開始時凍結案件／規則／語料基底；執行期間只能追加實際讀取的證據紀錄，結束時封存完整 manifest，不改既有輸入版本。長對話可摘要，但原訊息仍在，摘要不能改寫正式狀態。

### 3.3 內容超過可用長度

優先保留選取段、相關規則與使用者指令；再選擇最相關證據。超限時顯示哪些來源尚未讀完，必要時分回合處理。不得在來源截斷時仍寫「已核對全文」。

v1 初始預算：每 run 最多 8 次工具呼叫、最多讀入 12 個檢索片段、總輸入目標不超過 16,000 tokens，且永遠受供應商實際上限約束；這是可配置的工程起始值，不是模型性能結論。完整重生可按章節分批，但候選完成後才進整份採用。

## 4. 協調器與工具設計

v1 使用單一協調器及有限工具迴圈；不需要先建多代理人團隊。規則計算、索引檢索、來源讀取與合併驗證由程式實作，模型負責文字理解和候選內容。

```text
使用者要求＋範圍
  → 伺服器權限／版本檢查
  → 凍結案件基底，建立 context_manifest
  → 意圖路由
  → 查詢／開啟原文／試算（按需要）
  → 生成答覆或候選 patch
  → schema、範圍、證據與版本驗證
  → 答覆＋真實活動＋diff 提案
  → 使用者採用
  → 後端交易保存新版本
```

### 4.1 可提供給模型的工具

| 工具 | 輸入 | 輸出／限制 |
|---|---|---|
| `read_case_resource` | 目前案件的 resource ID／revision | 僅讀該案件授權資源；回傳已確認／未確認區分 |
| `read_selection_context` | target 及需要的相鄰區塊數 | 不擅自擴大可修改範圍；只增加讀取上下文 |
| `search_knowledge` | query、資料類型、版本／案件類型等 filters | 回候選 ID 與摘要、缺口；search 命中不代表讀過全文 |
| `open_source` | `source_ref`／chunk ID 與 release | 原文、頁碼、行號、hash、時效狀態；不存在即失敗 |
| `get_calculation_trace` | analysis ID、gate ID | 已執行的輸入、算式、規則版本與結果 |
| `simulate_case_change` | 目前版本＋候選事實／個案假設 | 純試算結果與受影響項目，**不寫入正式狀態** |
| `check_proposal` | 結構化候選與目標 | 回範圍、引用與依賴檢查；不能採用 |

`apply_proposal`、`save_human_review`、`submit_case` **不是模型工具**。使用者按採用／儲存後，前端走正式 API，後端再檢查權限和版本。

外部官方網站查詢定為可插拔能力：v1 本地知識庫先可用；若部署已提供外部查詢，才開放 `search_official_sources/open_official_source`。只查部署允許的官方來源；保存 URL、取得時間、回應摘錄與 hash。正式外部引用先註冊不可變來源快照，不直接使用模型生成 URL。外部工具未接通時，明示「僅查本地快照，未確認最新版本」，不偽造查詢成功。

### 4.2 每回合的可見活動

活動事件由工具包裝層寫入，不由模型自由敘述。每個 `tool_call_id` 有 start/result/error，顯示工具友善名稱、查詢目的、查詢詞、篩選條件、回傳數、實際開啟來源與耗時。私人案件內容不放入通用伺服器 log，案件內活動受同案權限保護。

例如：

```text
讀取：本案「送達日期」與人工註記
查詢：法規庫／關鍵字「送達」／指定版本
找到：3 個候選
開啟：其中 2 個原文段落（來源卡可點）
試算：使用候選日期，未改案件
提出：1 組事實修正提案，尚未採用
```

只有 `open_source` 成功的材料可列「已閱讀」；search 結果僅列「搜尋命中」。來源沒有任何證據支持所問問題時，成功的結論也可以是「本次未找到足夠依據」。

## 5. 查證與引用

### 5.1 四個不同檢查

| 狀態欄位 | 驗證什麼 | 不能推論成什麼 |
|---|---|---|
| `source_exists` | ID／版本對得上原文 | 法條必然適用本案 |
| `quote_matches` | 引文逐字對得上來源 spans | 引文足以支持整段結論 |
| `support_status` | 此來源與該主張的支持關係：`supported/partial/contradicted/unknown` | 已完成法律專家審查 |
| `temporal_status` | `verified_for_date/snapshot_only/unknown` | 抓到最新頁面就可套到歷史案件 |

`source_exists/quote_matches` 由程式檢查；`support_status` 若由模型判斷，標 `assessed_by: model`，不是司法結論。依據衝突時並列資料及差異，不能只保留支持原結論的來源。

### 5.2 輸出原則

- 解釋／查證答覆中的可驗證法律主張連到來源卡；缺證時明確表達不確定性。
- 引文與模型概述分開欄位，不用引號把模型改寫包裝成原文。
- 對目前法規、歷史版本與本案日期的適用性分開回答；只存在快照就維持 `snapshot_only`。
- 局部文字潤飾可沿用既有有效引用，不強迫無關搜尋；若改變法律主張、數字或結論，就升級為實質修改檢查。
- 草稿引用限目前勾選的依據；AI 新找到的來源可供查證，但需先加入勾選並建立新提案，或在同一不可拆的修改組內明確包含「加入依據＋修改段落」。
- 「已查資料」不表示「已驗證本案事實」。原件不足、立場不清、前後矛盾都可導致 `needs_input`。

## 6. 局部編修：從自然語言到安全 patch

### 6.1 候選格式

AI 不回一份任意 JSON Patch 讓後端盲目套用。v1 使用自有 allowlist 操作：`replace_text`、`replace_fact`、`add_citation`、`remove_citation`、`replace_document`。每項都指定 typed target、base revision、before value／hash、after value、原因、證據與依賴；未知 path 或操作拒絕。

局部文字修改以穩定 block ID 和 code point 範圍定位。相同句子出現兩次也只能改使用者選的那一處。段落 ID 或 hash 不符時返回 conflict，不以模糊字串搜尋自動覆蓋。

### 6.2 修改分類

`change_class` 有 `wording/fact/legal_assessment/citation/structure`。分類協助顯示影響；數字、否定、日期、條號、主文或採用依據改變，伺服器至少標記為需實質檢查，不能只相信模型自稱「純潤飾」。

操作分成 `change_groups`。同一法律命題的文字、引用與相關修正放同組，不能只接受文字卻拒絕其必要引用。使用者可以逐組採用；跨組依賴由後端驗證，不允許留下斷裂內容。

### 6.3 採用前驗證

1. schema 合法、資源屬於本案、操作與 intent／選取範圍相容。
2. 候選基底文字與已凍結版本一致；沒有修改不可變 PDF／正式規則庫。
3. 新引文存在、quote 對得上、必要引用已勾選或納入同組。
4. 數值改動若影響計算，保存 `simulate_case_change` 的結果；該結果仍是候選。
5. 依賴的 facts／analysis／selections／rules／KB 版本完整。缺依賴清單按整個案件快照保守檢查。
6. 生成器失敗或只輸出半段時，不建立可採用提案；可保存未完成回覆供查。

伺服器驗證失敗可把具體錯誤交回模型修正，最多 1 次；仍失敗就 `failed`，不得無限重試或直接套用未驗證內容。

## 7. 完整重新生成

完整重生的目標是指定工作文件，例如草稿，而非重置整個案件。取得目前事實、系統分析、有效人工覆核、勾選依據、註記意圖及文件格式；形成不可變 `GenerationInput`。

使用者可選「保留已採用的人工段落」或「提出全文新寫法」。即使選全文新寫法，也只產生候選；目前文件不會在生成途中消失。預設保留人工段落，並顯示其是否因事實變動需要重查。

完整生成後按 stable block ID 對照 base／current／candidate：增刪段落、移動、引用改動、事實差異分別列出。模型不能任意為所有段落換 ID 來躲掉差異。無法匹配的新結構標為新增／刪除，交由人判斷。

完整重生和局部修改最後都使用同一套 proposal／merge／apply API，避免形成兩套版本來源。採用前如依賴已更新，重做候選或人工解決衝突；**文件 diff 沒衝突不等於法律依據仍有效**。

## 8. 提示詞與供應商介面

提示詞以有版本的四層組成：系統職責與工具邊界、該 intent 的任務契約、目前案件與來源資料、使用者要求。來源文件／註記標成資料，不得因其中寫著「忽略規則」「改其他案件」就取得工具權限。

局部改寫模板至少含下列要求：

```text
任務：依使用者要求提出指定範圍的修改候選。
可修改範圍：伺服器核准的 target；範圍外只能提出需要調整的說明。
證據：只能引用提供且已開啟的 evidence IDs；不要捏造來源。
事實與結論：不能把潤飾升格為未經說明的事實／法律變更。
輸出：answer、change_groups、evidence_refs、unresolved_questions。
狀態：你沒有執行正式寫入，請使用「建議修改」而非「已修改」。
```

程式驗證是必要控制；提示詞不是引用正確與權限安全的唯一防線。記錄 `prompt_version`、模型識別、參數、token 用量與工具結果 hash；不記錄或顯示供應商憑證。

維持既有可替換 Provider 方向。所需抽象能力是結構化生成、文字串流與可選工具呼叫；若模型不支援原生工具呼叫，由協調器按結構化結果選工具。預設沿用專案已配置供應商，模型名稱／配額／價格以實作時驗證為準，不在規格硬編舊型號。

## 9. Run、串流、取消與失敗

run 狀態：`queued/running/completed/failed/cancelled/needs_input`。run 完成只代表答覆／提案完成；正式修改是否成功看 proposal 的 `applied` 狀態。

- 使用者送出訊息後立即得到 `run_id`，可透過事件串流看到讀取、搜尋、來源與文字輸出。
- 文字 token 串流屬暫時內容；最終 schema／引用檢查成功才出現可採用提案。
- 斷線重連依事件序號補送，不重跑整個模型，也不重複產生提案。
- 取消只終止尚未完成的 run；已完成修改不因關閉側邊欄撤回。
- 生成時使用者改了資料，run 可完成候選，但標「依舊版本產生」；採用時必須重驗證／合併。
- 供應商中斷：人工編輯、註記與既有引用預覽仍可用；查詢可用本地 BM25，不能假造 AI 答覆。
- 配額／工具限額達到：顯示已查範圍與尚未解決問題；重試需要新 run 或同一請求的安全續行，依 API 冪等規則。

初始總逾時 120 秒、單工具 20 秒，均為部署可調參數；工具開始與結束需可觀測。v1 暫以每案同時一個會產生修改提案的 run，其他進佇列；純讀取對話可並行。這是降低互撞的排程，不取代版本檢查。

## 10. 三個完整互動情境

### A. 質疑日期與分析

1. 選取送達日期，加註「這可能只是文件上的另一個日期」。
2. AI 讀日期來源、使用者註記與對應計算紀錄，搜尋並開啟相關來源。
3. 缺送達證據：AI 回報缺口並要求定位，沒有日期更正提案。
4. 使用者補上可定位資料後，AI 提出 `replace_fact`，並以候選值試算。
5. diff 顯示原日期／候選日期與受影響算式；使用者採用後才保存事實版本。
6. 後端重算產生新的 system result；如需人工法律覆核，由人另外保存，不冒充 AI 算出確定法律結論。

### B. 修改一段理由

1. 選取草稿一句，要求「語氣更正式，但不要改意思」。
2. AI 讀該段、相鄰必要脈絡與既有引用，不必無關地查整個庫。
3. 回傳一組 `wording` 提案，顯示刪除／新增內容與不變引用。
4. 使用者先改了同一句：採用回 conflict，展示三方差異；另段編輯則可預覽合併。
5. 採用後活動才顯示「已套用至草稿 v8」。

### C. 完整重生

1. 事實已更新，舊草稿標過期；使用者選完整重生。
2. AI 讀目前已確認事實與勾選依據，保留人工段落偏好，生成候選。
3. UI 顯示哪些段落因新事實改變、哪些人工段落仍保留／需檢查。
4. 使用者依修改組採用；後端保存 parent、candidate 與合併結果關係。
5. 全部必要依賴都已重算／覆核後，草稿才可標為目前有效；只改幾句不會自動解除整份過期。

## 11. AI 專項驗收

固定測例含：有／無來源、來源互相衝突、法規時效未知、範圍外改動、相同句子兩次、混合文字與日期變更、PDF 中的惡意操作指令、跨案 ID、並行人工編輯、取消、超時、斷線重連及完整重生。

硬性門檻：測例中跨案讀寫為 0、未採用即改正式內容為 0、範圍外修改為 0、偽造已查來源為 0、無聲覆蓋人工修改為 0。所有採用修改能回查 base／run／證據／操作者／結果版本。這些是測例門檻，不是系統永遠零錯誤的保證。

引用逐字核對全自動；支持關係與法律適用另由人工抽驗，分開報告。文字流暢不等於正確；來源存在也不等於支持結論。交付時記錄測例數、通過率、延遲、用量與未驗證範圍。
