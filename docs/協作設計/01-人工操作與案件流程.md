# 人工操作、註記與案件流程

日期：2026-09-12｜v1.0 設計｜依據：[U1–U6](README.md)

## 1. 工作方式

承辦人在案件頁面直接閱讀、修正、加註與詢問 AI。頁面不是只能看一次的分析報告，而是有版本紀錄的工作文件。側邊欄可用於擷取結果、程序檢核、法規推薦與草稿；切換畫面保留同案對話，切換案件則切換對話範圍。

人工可直接修改，不必先取得 AI 同意。AI 修改以 diff 提案呈現，使用者可採用、逐組採用、拒絕，或編修候選後採用。這是 v1 預設互動；不提供跨案件或全面自動套用模式。

## 2. 主畫面與側邊欄

| 主畫面操作 | 側邊欄接到的內容 | 可產生的結果 |
|---|---|---|
| 選取一句草稿 | 文件／區塊／版本與選取文字 | 解釋、改寫提案、引用查證 |
| 點選期間計算的一個數值 | 欄位 path、輸入來源、對應算式 run | 解釋算式、修正輸入提案、情境試算 |
| 對某款加註 | gate ID、註記、現行事實與規則版本 | 補證建議、來源查詢、人工覆核草案 |
| 選取 PDF 原文 | 不可變原件的 source spans | 解釋、對照、提出擷取更正；不覆寫原件 |
| 點「完整重新生成」 | 明確目標文件、目前事實／勾選與版本 | 完整候選文件與 diff |

選取後顯示可移除的範圍提示，例如「本案／理由第三段／已選 42 字／v7」。提供「解釋這段」「查證依據」「修改這段」「加註記」；使用者也可自由輸入。未選取時預設只針對目前案件提問；要求修改但目標不明時，AI 應要求定位，不能自行修改全文。

側邊欄顯示：訊息、引用、查詢活動、候選修改與採用狀態。正在執行時可取消；離開畫面不等於取消。來源卡可跳回 PDF 頁碼及行號；正在看舊版本時明示版本。

## 3. 可以改哪些內容

| 內容 | 直接編輯的語意 | 保存後動作 |
|---|---|---|
| 擷取欄位，例如送達日期 | 人工修正事實；保留原抽取值與新值 | 建事實版本、標記相關分析過期並排程重算 |
| 草稿句子 | 人工文字編修 | 保存新草稿版本；重新檢查引用，保留原內容 |
| 註記 | 意見／疑問／補充材料，不自動變成已確認事實 | 保存註記；可另外送 AI 討論 |
| 期間、在途日數等規則輸入 | 個案規則假設或人工採用值 | 要有理由／來源；試算後由人採用，不修改共用規則庫 |
| 計算輸出，例如逾期天數 | 不能只改顯示字串；建立人工覆核／試算提案 | 展示與系統算式差異，要求關聯輸入或覆核理由 |
| 程序檢核狀態 | 個案人工覆核結果 | 保留原系統結果，記人工結果及理由，重算案件分流 |
| PDF／知識庫原文 | 原件不可變；可改工作副本／更正擷取註記 | 更正附來源，新抽文版本不冒充原件內容 |

**直接編輯的可見位置不等於所有欄位都只是文字。** 使用者在同一個數值旁按「修改」，系統依欄位種類顯示事實修正、試算或人工覆核表單；不能出現畫面寫未逾期、後端仍用舊日期判逾期的狀況。

手動草稿編輯在失焦／短暫停止輸入後自動保存；只在伺服器成功回覆後顯示「已儲存」。斷網則標未同步並保留編輯緩衝。未保存範圍不可送 AI 修改，先保存或明確使用一次性的討論草稿。

## 4. 註記與人工覆核分開

註記有 `open/resolved` 狀態，錨定文件版本、欄位或 gate。使用者可以寫「這個日期可能是寄存日，請確認」，再按「送 AI 查證」。這只增加討論材料，不會改日期或自動解除黃燈。

AI 回答與提出修改後，使用者可：

1. 只保留註記與答覆。
2. 採用事實／文字修改。
3. 保存人工覆核：指定款別、結果、理由與證據／尚無文件佐證的聲明。

人工提供的說法標 `human_asserted`，不能冒充文件擷取；可作試算，但需要文件證據的檢核不能因此自動聲稱已驗證。缺證但需暫時處理時保留人工責任與不確定性，不能強迫使用者編造來源。

同案同款可有多次覆核，新的覆核取代舊的有效覆核，但舊紀錄可查。與該款相關的事實或規則變動後，原覆核標過期，需再次確認。

## 5. 單款結果與案件分流

單款並列三層：`system_result`（規則引擎）、`ai_assessment`（AI 建議，可能為 null）、`human_review`（有效人工覆核，可能為 null）。`effective_outcome` 由後端取有效人工覆核，否則取現行 system result；AI 說「應改成不成立」本身不能改 effective outcome。

沿用五種 outcome：`NOT_TRIGGERED/TRIGGERED/NOT_APPLICABLE/INSUFFICIENT_EVIDENCE/NEEDS_HUMAN`。對依既有設計需人工法律判斷的款別，AI 可提出依據與建議，原系統待人工結果保留；人工可在原畫面完成覆核。

v1 案件級分流如下；這是工具工作流程，不是新增法律規則：

| 條件，按順序判斷 | `workflow_state` | 畫面與可執行操作 |
|---|---|---|
| 相關事實已變動，分析未完成或版本不符 | `analysis_pending` | 顯示舊結果＋過期標記；可討論，不能以舊結果送審 |
| 同一爭點存在未解決的事實衝突，或有效結果需補證／人工確認，且沒有已確認的觸發依據 | `human_review` | 原畫面加註、補證、討論、人工覆核 |
| 至少一款有效 `TRIGGERED`，觸發依據沒有未處理衝突 | `procedural_draft` | 可準備不受理工作草稿；其餘未決事項仍列出，送審需承辦人確認採用依據與處置理由 |
| 無有效觸發，所有款均為 `NOT_TRIGGERED` 或 `NOT_APPLICABLE` | `substantive_recommendation` | 可進實體推薦與後續草稿 |
| 以上條件無法明確判別 | `human_review` | 不猜測放行 |

如果使用者否定唯一的觸發款，但其他款仍待確認，回 `human_review`，不是直接跳到實體審查。若衝突影響觸發款本身，該款不能當作已確認觸發依據。多項請求／複合結果保存 `issue_scope_id`，分流按範圍處理；v1 無法拆出範圍時，整案轉人工，不用單一旗標覆蓋所有請求。

在 `human_review` 仍可閱讀、加註與編修既有工作草稿；不能藉由 AI 文字改寫繞過正式分流。畫面「送陳核」是獨立動作，確認目前事實、結果、未決事項與草稿版本後建立內部送審快照，不等於政府機關完成法定決定或發文。

## 6. diff 的兩種體驗

**局部修改：**選句→要求調整→候選句與差異→採用該修改組。範圍外文字不應變動。若 AI 發現還需修另一段，另外提出範圍擴充，不偷偷附帶修改。

**完整重新生成：**選擇要重生的工作文件，例如整份草稿→顯示採用的事實／勾選版本→產生完整候選→逐段 diff 與人工修改提醒→逐組採用或整份採用。完整重生不等於刪除註記、對話與人工覆核，也不會改原件。

若另一位承辦人或另一分頁已編輯同一段，顯示「產生提案時版本／目前版本／AI 候選」三欄。可保留目前內容、採用候選或手動整合；任何選擇都建立新版本。沒有衝突才可一鍵採用，不以最後寫入者直接覆蓋。

## 7. 必須做的互動驗收

- 直接改日期後，日期已儲存、相關算式待重算，兩種狀態可辨識。
- 註記可獨立保存，送 AI 討論不會暗中改事實。
- 局部改寫只改選取範圍，未採用前正文不變。
- 修改內容後可查看「誰、何時、從什麼變成什麼、根據何來源」。
- 新版移動段落時註記仍可定位；刪除原段落則標「原位置已不存在」，不錯貼到同文句。
- 同時保留系統結果、人工覆核與 AI 建議，UI 不把三者都稱為「AI 信心 100%」。
