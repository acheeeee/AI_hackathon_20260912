## 3. 不要打破的約定

這幾條是階段 A 的設計決定，違反會讓已通過的驗收案例失效。

1. **交易邊界在路由層。** service 的寫入函式假設呼叫端已經開好交易。所有會改狀態的端點都走 `api/mutation.py` 的 `execute_mutation`，它負責：冪等查詢 → 單一交易內執行 operation → 在同一筆交易寫入冪等回應。不要在 service 裡自己開交易。
2. **每個請求一條 SQLite 連線**（`api/deps.py` 的 `get_db`）。不要改成共用單一連線，sqlite3 連線不是執行緒安全的。
3. **不要用 `executescript` 包在 `transaction()` 裡。** Python 的 `executescript` 會先隱式 commit，會把你開的交易關掉，接著 COMMIT 會報「no transaction is active」。migration 執行器因此刻意不開交易。
4. **`advance_case` 是推進版本的唯一入口**，它用 `WHERE case_revision = expected` 更新並檢查恰好一筆，同時寫 case_snapshot。不要繞過它直接 UPDATE cases。
5. **heads 的形狀**是 `{resource_id: {revision_id, kind, freshness}}`，存在 `cases.active_heads_json`。`freshness` 屬於目前指標，不屬於版本內容，所以不在 `resource_versions` 裡。所有 heads 操作（`set_head`、`mark_stale`）都回傳新的 dict，不就地修改。
6. **資源版本不可變。** 內容變動一律新增 `resource_versions` 一列，`parent_id` 指向前一版。註記的每次編修也是存成 `resource_kind='annotation'` 的新版本。
7. **人工文字編輯不解除 stale。** 只有 `POST /drafts/{id}/reviews` 帶理由才會把 freshness 改回 current。
8. **合併在預覽階段算完，採用交易只複核。** `merge_service` 產生不可變的 `merge_previews` 一列與 `preview_hash`；`apply_service` 只驗 preview 歸屬、案件版本、hash、組依賴閉包與是否已套用，然後寫版本。昂貴的計算不要搬進採用交易。
9. **有衝突時預覽的候選內容要保留目前版本。** `_Merger` 在衝突分支也會把 current 內容放進 `working`，否則人工整合端點會找不到資源可改。
10. **錯誤碼照 [04 §7](04-API契約.md)。** 已用到的對應：缺欄位或欄位不合規 422 `INVALID_FIELD`；壞 JSON 400 `MALFORMED_REQUEST`；候選越界或基底不符 422 `OUT_OF_SCOPE_PATCH`；引用不存在或必要引用組沒一起採用 422 `INVALID_CITATION`；案件或資源版本過期 409 `REVISION_CONFLICT`；依賴事實已變 409 `DEPENDENCY_STALE`；區塊不在該版本 409 `TARGET_MOVED`；重複採用同組 409 `PROPOSAL_ALREADY_APPLIED`；終態 run 再取消是 409 `RUN_NOT_CANCELLABLE`；跨案與不存在一律 404 `RESOURCE_NOT_FOUND`。
11. **身分只從伺服器設定來。** `get_actor_id` 讀 Settings，前端不能指定 actor。要換成真登入就改這個 dependency，不要讓 actor_id 進入請求體。
12. **測試風格**：Arrange-Act-Assert，測試名稱描述行為。新功能先寫測試（RED），再實作。`tests/conftest.py` 有 `mutate`、`create_case`、`create_draft`、`proposal_body` 等 helper，冪等鍵預設自動產生，要測重送才自己指定同一把。**`TestClient` 綠燈不等於真的能跑。** 2026-09-13 發現：`caseapi/db/connection.py` 的 `connect()` 原本沒加 `check_same_thread=False`，83／92／104／122 項測試全數通過都沒發現，因為 Starlette 的 `TestClient` 不會重現真正用 `uvicorn` 跑時，FastAPI 把同步 generator dependency（`api/deps.py` 的 `get_db`）的建立與收尾分派到 anyio threadpool 不同 worker thread的行為；直到第一次真的啟動 `uvicorn` 並用瀏覽器打 `GET /cases/{id}` 才炸出 `sqlite3.ProgrammingError`。**新增會被前端直接呼叫的端點時，除了 `pytest`，至少手動啟動一次真正的 `uvicorn` 並用瀏覽器或 `curl` 打過一輪，不能只看 `TestClient` 綠燈就當作驗證完成。** 修法與重現測試在 `tests/test_db.py::test_connection_survives_being_closed_from_a_different_thread`。
13. **run context 建立後凍結；事件只能由伺服器執行層追加。** `run_events.sequence` 在每個 run 內單調遞增，重新讀取用 `after_sequence`，不重跑工作。`provider_config_json` 只存 provider／model 等非秘密設定，service 會拒絕 credential 類欄位。
14. **search 與 open 不是同一證據狀態。** `search_knowledge` 只寫 `tool.started/completed`，不寫 evidence；只有 `open_source` 成功時能在同一交易寫 `source.opened` 與 `assessed_by=program` 的 evidence。這只證明來源存在與 quote 一致，`support_status` 仍為 `unknown`。
15. **`ModelProvider`／`ToolGateway` 是 provider 換血的唯一邊界。** `execute_chat_run`（`ai/runner.py`）只認 `caseapi.ai.contracts.ModelProvider` 這個 Protocol；`ToolGateway` 把 `case_id`／`run_id` 綁死，provider 不能指定別的案件。接線上 provider（AgentCore／Bedrock）時新增一個實作這個 Protocol 的類別即可，**不要改 runner 或 routes_chat 去繞過這層**，也不要讓 provider 直接拿到 DB 連線或案件 repository。`descriptor()` 回傳的字典只能放 provider／model／region 這類非秘密設定；憑證一律在 provider 內部用 `os.environ` 現讀現用，不進 `provider_config_json`（見規則 13 的 credential 拒收）、不進 log。
16. **`fail_run` 對已終態的 run 是 no-op，不是錯誤。** 這是 B3 收尾修的一個真競態：run 被使用者取消後，若背景中的 provider 仍在同一次 `execute_chat_run` 裡把結果寫回，`complete_run` 會因狀態已非 `running` 而丟出例外；原本的例外處理再呼叫 `fail_run`，若它也對非 `running` 狀態丟例外，第二個例外沒人接住，會直接穿出背景工作（Starlette 的 `BackgroundTasks` 不會幫你接）。現在 `run_service.fail_run` 對已在 `TERMINAL_STATES` 的 run 直接回傳現況，不改狀態也不重覆寫事件。**`fail_run` 只由 `ai/runner.py` 的例外處理呼叫，不是使用者可觸發的 API，之後新增呼叫點前要重新確認這個假設還成立。** 對應測試：`tests/test_fixed_model_e2e.py::test_cancelling_a_running_run_survives_a_provider_that_finishes_late`，重現方式是讓假 provider 在 `execute()` 內部直接呼叫 `run_service.cancel_run` 模擬使用者在模型思考時取消。

## 4. 已知偏離與待回寫契約

這三個端點的實作語意已回寫 [04](04-API契約.md)，但前兩個仍是階段 A 為了驗證流程而加的暫時入口，不等於正式 run 流程：

| 端點 | 為什麼加 | 之後怎麼辦 |
|---|---|---|
| `POST /api/v1/cases/{case_id}/drafts` | 沒有草稿就測不了編輯與 diff | 正式流程改由抽文／生成建立；目前保留作階段 A 入口 |
| `POST /api/v1/cases/{case_id}/proposals` | 契約的提案由 run 產生，那是階段 B 之後 | B3 只證明 `verify`／`explain` 兩個 intent，還沒有一個 intent 會產生 proposal；接線上 provider 且要做草稿生成時，這個 fixture 入口應限測試用或移除 |
| `POST /api/v1/cases/{case_id}/drafts/{draft_id}/reviews` | 保存一個新版本並把 freshness 改回 current | 已與 04 對齊；規則引擎完成後再加入必要分析未完成時的阻擋 |

其他缺口：

- **B3 的 fixed provider 只支援 `verify` 與 `explain` 兩個 intent，不產生 proposal。** 要用 AI 生成或修改草稿內容（規劃裡的「選取草案內容叫 AI 解釋或修改」）需要新增第三種 intent，並讓它的結果走 `proposal_service` 產生可採用的提案，而不是像現在直接把 `ModelResult.answer` 存成聊天訊息了事。
- **背景協調器是 Starlette `BackgroundTasks`，不是可恢復 worker。** 服務中止時 running 的 run 永遠停在 running，`lease_until` 過期也沒有回收機制。demo 錄影如果會重啟後端，這個要先補一個啟動時掃描過期 lease 並標記 failed 的步驟，否則畫面會留下卡住的轉圈。
- **SSE 是「補送已存事件後關閉」，不是等待新事件的長連線。** `GET /runs/{id}/events?format=sse` 目前行為等同一次性把 `after_sequence` 之後的事件轉成 SSE frame 就結束串流；瀏覽器要看到「思考中→查詢中→完成」的漸進效果，需要前端自己用假的時間軸配合這批已存事件呈現，不是後端真的在串流。使用者已確認 demo 走錄影、前端動畫可以是假的時間軸，但畫面上列出的「查了哪些資料」必須來自真事件，不能編造。
- **Evidence adapter 的查證寫入路徑已由 fixed run 使用，但 support_status 仍是 `unknown`。** `open_source` 只證明來源存在與 quote 一致，不判斷是否支持本案主張；線上 provider 也不該假裝能回答這件事，除非另外設計一個明確的法律判斷欄位並要求人工覆核。
- **同一區塊的字元級自動合併沒做**，依 [03 §6.1](03-後端SQLite與版本合併.md) 規則 3 保守視為衝突。完整文件衝突也是整份判定。
- **沒有 `PATCH /selections`**，引用是否齊備只靠修改組依賴閉包把關。
- **`gate_result` 與 `source_span` 兩種 TargetRef 只驗形狀**，不驗目標存在，因為沒有 analyses 與來源快照表。
- **沒有規則引擎。** 事實變動時保守把所有草稿標 stale，這是 H01 只能標 `PASS＊` 的原因。
- **舊後端 `backend/api.py`／`backend/src/` 的 PDF 抽取、期限檢查與 `/api/draft` 模板草稿完全獨立於新後端**，新後端目前沒有上傳 PDF、抽欄位或期限檢查的端點；這是下一批要補的（見 §5）。

### 5.2 前端能上場的七個項目（依使用者指定順序，逐項獨立 RED／GREEN／commit）

1. **上傳建案（已完成，2026-09-13）。** `POST /api/v1/cases/intake`（multipart：`appeal_pdf` 必填、`disposition_pdf` 選填、`title` 選填）建立案件、把兩份 PDF 存進新的 `case_documents` 表（含原始位元組，供之後「原檔展開」）、用 `caseapi/domain/appeal_extraction.py` 對訴願書全文做規則式抽取，把抽到的欄位寫成 facts 資源的第一版（`origin='program'`）。**只抽訴願書，不抽行政處分函**：訴願書是固定格式的行政院標準表單，逐案校準過 6 份 `data/raw/訴願書予行政處分函-1/` 真實樣本全部正確；行政處分函格式不固定，存原件但不抽欄位，交人工或之後另外授權的 AI 輔助抽取。抽不到的欄位（`appellant.address`、`service.date`、`service.method`）留 `None`，不猜。`GET /api/v1/cases/{case_id}/facts` 一併補上，讀目前 facts 欄位。
2. **案件列表（已完成，2026-09-13）。** `CaseSummary`／`CaseDetail` 新增 `processing_status`（`unprocessed`／`processing`／`completed`），在 `case_service._processing_status` 讀取當下依 heads 有沒有 draft、audit_entries 有沒有 `draft.reviewed` 動作即時算出，沒有新增欄位或狀態機表。
3. **原檔展開（已完成，2026-09-13，原本是階段四的範圍，因為案件列表點進去需要有地方去而提前做）。** `GET /api/v1/cases/{case_id}/documents`（列表，不含 blob）與 `GET .../documents/{document_id}/content`（回傳原始 PDF bytes，`Content-Type: application/pdf`，跨案或不存在一律 404）。前端 `CaseDetailView.vue` 用 `<iframe>` 嵌瀏覽器原生 PDF viewer 顯示，兩份文件用 tab 切換，不做自製的 PDF renderer。
4. **前端首頁與案件詳情頁（已完成，2026-09-13）。** `frontend/src/views/HomeView.vue` 取代原本的五步驟精靈當首頁：案件卡片列表＋狀態標籤＋「上傳新案件」對話框，拿掉了 `demoCases.ts` 的「選 demo」入口（該檔案還在，只是新首頁不再引用）。`CaseDetailView.vue` 顯示抽取事實與原始文件。舊的五步驟精靈搬到 `/legacy-demo`（路由名稱仍是 `wizard`），繼續走舊後端 `/api/*`，兩邊不共用狀態；`vite.config.ts` 新增 `/api/v1` proxy 指到新後端（`:8001`），排在舊的 `/api` proxy（`:8000`）之前。
5. **側邊欄 AI 對話（已完成，2026-09-13，原本排在程序審查後面，因為後端已經全部做好、風險最低而提前）。** `frontend/src/components/ChatSidebar.vue` 掛在 `CaseDetailView.vue`，右下角浮動按鈕開關。純前端接線，B3／AgentCore 的聊天後端一行都沒改：送訊息、輪詢 `GET /runs/{id}`（每 600ms，最多 40 次，沒有真 SSE）、完成後讀 `GET /runs/{id}/events` 把 `tool.started`／`tool.completed` 配對成人看得懂的一行（`frontend/src/utils/runEvents.ts`，有單元測試），再讀 `GET messages` 拿真的 assistant 回覆。**思考中／查詢中只是前端假的節奏，顯示的每一行「查了什麼」都來自真事件**，事件裡沒有對應的 `tool.started` 就不猜、不畫那一行（見 `runEvents.spec.ts` 的測試）。事實欄位旁加了「問 AI」按鈕，用 `fact_field` 目標打 `explain` intent——這連帶修了一個真的缺口：`FixedModelProvider`／`AgentCoreModelProvider` 的 `_explain` 原本只認 `draft_block` 目標的 `selected_text`，對 `fact_field` 目標永遠讀到空字串，因為欄位值其實在 `read_selection_context` 回傳的 `context.field` 裡，不在 `writable_target` 上；新增 `caseapi/ai/selection_text.py` 統一處理兩種目標，兩個 provider 都改用它。真瀏覽器手動測過 verify（自由提問）與 explain（點欄位問 AI）兩條路徑，AgentCore 都給出誠實、有依據或明說查不到的回答。
6. **程序審查（已完成，2026-09-13；範圍是訴願法第14條三十日期間試算,不是完整的第77條各款不受理事由）。** `GET /api/v1/cases/{case_id}/procedural-review` 讀取當下 facts 即時算出，不持久化、不建 `analyses` 表——跟 `processing_status` 同一種作法。`caseapi/domain/appeal_deadline.py` 是純函式：`service.date` 缺就回 `insufficient_data`，**不拿 `disposition.date` 頂替**——處分日期不等於送達日期,用它算會低估期限,可能把還沒過期的案件誤判成逾期,這個風險不值得為了少一次人工填值去冒；`service.date` 有、`appeal.filed_date` 沒有就回 `deadline_known_filing_unknown`（給期限但不判斷是否逾期）；兩者都有才回 `within_period`／`overdue`。只算日曆天數,不處理國定假日順延（行政程序法§48 IV 需要假日曆,沒有就在 `caveats` 裡明說,不裝懂）。回應固定帶 `legal_review_status: 'not_reviewed'`，contract 測試斷言輸出字串裡不能出現「不受理」。前端 `ProceduralReviewPanel.vue` 掛在 `CaseDetailView.vue`，缺欄位時給一個小表單直接呼叫既有的 `PATCH /facts`（走 `human_asserted: true`），不是新的寫入路徑。四種狀態都用真瀏覽器對真後端測過（`insufficient_data`→`deadline_known_filing_unknown`→`overdue`→`within_period`），逾期天數與期限日期都對得上手算結果。**`GateResultTarget`／AI 側邊欄的 explain 沒有接這個結果**：那需要一張快照表才能讓目標的 `analysis_id`/`gate_id` 可驗證存在（見 §4 那條「只驗形狀不驗目標存在」的舊缺口），這次為了不新增表格所以沒做，留給下一次真的要在側邊欄解釋程序審查結果時再處理。第77條其餘各款（其他不受理事由）也還沒做，只做了期間這一款。
7. **選法規（已完成，2026-09-13）。** `GET /cases/{case_id}/statute-search?q=`（可省略 `q`，省略時用 `caseapi/domain/appeal_extraction.py` 新增的 `extract_case_narrative` 從訴願書事實／理由段落抽出查詢字串，不是整份文件也不是憑空生成）對 r3 語料做真的 BM25，`document_types={'statute'}`。**搜尋本身不寫 evidence／run 事件**——這是人工瀏覽候選，不是 AI 工具呼叫；之後真的拿去當草稿依據才需要走 `EvidenceToolAdapter.open_source` 補上 program-verified 的驗證，見規則 14。人工挑選結果存成新的資源種類 `statute_selection`（`case_repository.KIND_STATUTE_SELECTION`），沿用既有 `resource_versions`／heads／`advance_case` 機制，`PUT /cases/{case_id}/statute-selection` 整批覆蓋、不是逐筆增刪，跟 facts 的欄位式 PATCH 不同語意。前端 `StatuteSelectionPanel.vue` 掛在 `CaseDetailView.vue`，搜尋框預先帶入建議查詢、可自行修改重新搜尋。真瀏覽器對真後端測過：預設查詢字串正確抽出案件的事實理由段落，搜尋結果第一筆就是案件理由裡實際引用的洗錢防制法第6條，加入、儲存、重新整理後仍保留都驗證過。
8. **草稿生成（尚未開始）。** 把 5.1 節做出的線上 provider 接進一個新的 intent（例如 `draft`），透過 `proposal_service` 產生真提案，取代目前階段 A 的 fixture `POST /proposals` 入口；草稿生成時應該把這裡選定的法規當作 context 或依據，不要重新設計一套法規來源。

完成 5.1、5.2 之後，[05 §3](05-實作順序與驗收.md) 的 A05、A06、A07 才有機會從 NOT RUN 移動；**改狀態時要附實跑證據，不能因為程式寫好了就標 PASS。**

## 7. 下一輪（尚未開始）：草稿生成、手動編輯、選取叫 AI 解釋或修改、UI 打磨、刪除舊後端

下面五個小節（§7.1–§7.5）是使用者下一輪指定要做的範圍。其中兩項（§7.2 手動
編輯草稿、§7.3 選取文字叫 AI 解釋或修改）**目前完全沒有前端實作**，容易被誤
以為「已經有草稿生成就順便有了」——不是，這裡分開說清楚各自缺什麼。

### 7.1 草稿生成

把 5.1 節的線上 provider 接進一個新的 intent（例如 `draft`）：

- 目前 `FixedModelProvider`／`AgentCoreModelProvider` 只認 `verify`／`explain`；新增
  intent 時兩個 provider 都要處理，且結果要透過 `proposal_service` 產生真正的
  proposal（有 `groups`／`EvidenceRef`，見 [04 §3](04-API契約.md)），不是像
  `verify`／`explain` 那樣把 `ModelResult.answer` 直接存成聊天訊息就結束。
- context 至少要包含：目前 facts（`facts_service.read_current_fields`）、選定的
  法規（`statute_selection_service.get_selection`，見 §5.2 第 7 項）、原始訴願書
  文字（`case_documents.extracted_text`）。程序審查的期限試算結果（§5.2 第 6 項）
  要不要放進去、放多少，這是法律內容判斷，本文件不替你決定，留給實際做的人跟
  使用者確認。
- **`POST /api/v1/cases/{case_id}/drafts` 這個階段 A fixture 入口該退場了**（見
  §4 表格）：真正的草稿建立應該由這個新 intent 觸發，而不是由前端直接呼叫
  fixture 端點生一個空白草稿。
- 前端需要一個「產生草稿」的觸發點（放在 §5.2 第 7 項選法規完成之後很合理）與
  一個處理中畫面——使用者原話是「選擇相關法規之後跳一個處理畫面，然後生成
  草稿」。這個畫面可以照 `ChatSidebar.vue` 已經驗證過的作法：假的時間軸節奏
  （思考中／生成中），但只要畫面上出現「參考了哪些法規／哪些事實」，就必須
  是真資料，不能編。

### 7.2 手動編輯草稿——目前完全沒有前端，不要以為草稿生成順便就做掉了

後端的編輯端點（`PATCH /api/v1/cases/{case_id}/drafts/{draft_id}`，
`draft_service`）是階段 A 就做好的，這次全程沒動過，也没被任何新前端頁面呼叫
過。新前端目前沒有任何畫面能「看草稿內容」，更不用說編輯。這裡要做：

- 一個顯示草稿區塊（blocks）內容的畫面／面板（掛在 `CaseDetailView.vue` 或另開
  一個路由都可以）。
- 區塊文字的就地編輯，呼叫既有的 `PATCH /drafts/{draft_id}`。
- 重新生成草稿、但草稿已經有人工修改時的三方 diff／衝突處理——`merge_service`／
  `apply_service` 這套機制階段 A 就做完且測過（見驗收表 V01–V05），這裡只是
  終於要接上前端。如果時間不夠，至少要能處理「沒有衝突」的簡單路徑，並且**明確
  告訴使用者衝突情境（V01／V02）沒做前端，不要沉默跳過**。

### 7.3 選取文字叫 AI 解釋或修改——「解釋」缺前端，「修改」缺後端

- **解釋**：`FixedModelProvider`／`AgentCoreModelProvider` 的 `_explain` 本來就認得
  `draft_block` 目標（在這次上工之前就有，`ChatSidebar.vue` 目前只從「事實欄位」
  發起 explain，用的是 `fact_field` 目標）。要讓「選草稿裡一段文字問 AI」動起來，
  純粹是前端工作：在草稿檢視畫面裡抓瀏覽器的文字選取範圍，算出
  `char_start`／`char_end`／`selected_text`／`selected_text_sha256`（sha256 算法
  見 `caseapi/schemas/target.py` 的 `DraftBlockTarget`），組成 `DraftBlockTarget`
  丟給既有的 `ChatSidebar`（可能需要讓 `ChatSidebar.vue` 或呼叫端能接受任意
  `TargetRef`，不是只硬寫 `fact_field`）。
- **修改**：目前不存在。要讓 AI 對選取範圍提出修改建議並且能被採用，語意上是
  §7.1 的 `draft` intent 的一個變體（範圍限定在選取的區塊，且要通過既有的
  `OUT_OF_SCOPE_PATCH` 邊界驗證——見驗收 A01／A02），不是聊天答案。這是這五項
  裡設計難度最高的一塊，會動到 §7.1 與 §7.2 兩邊的機制，建議排在 §7.1、§7.2
  都做完之後再做。
