## 3. 不要打破的約定

這幾條是階段 A 的設計決定，違反會讓已通過的驗收案例失效。

1. **交易邊界在路由層。** service 的寫入函式假設呼叫端已經開好交易。所有會改狀態的端點都走 `api/mutation.py` 的 `execute_mutation`，它負責：冪等查詢 → 單一交易內執行 operation → 在同一筆交易寫入冪等回應。不要在 service 裡自己開交易。
2. **每個請求一條 SQLite 連線**（`api/deps.py` 的 `get_db`）。不要改成共用單一連線，sqlite3 連線不是執行緒安全的。
3. **不要用 `executescript` 包在 `transaction()` 裡。** Python 的 `executescript` 會先隱式 commit，會把你開的交易關掉，接著 COMMIT 會報「no transaction is active」。migration 執行器因此刻意不開交易。
4. **`advance_case` 是推進版本的唯一入口**，它用 `WHERE case_revision = expected` 更新並檢查恰好一筆，同時寫 case_snapshot。不要繞過它直接 UPDATE cases。
5. **heads 的形狀**是 `{resource_id: {revision_id, kind, freshness}}`，存在 `cases.active_heads_json`。`freshness` 屬於目前指標，不屬於版本內容，所以不在 `resource_versions` 裡。所有 heads 操作（`set_head`、`mark_stale`）都回傳新的 dict，不就地修改。
6. **資源版本不可變。** 內容變動一律新增 `resource_versions` 一列，`parent_id` 指向前一版。註記的每次編修也是存成 `resource_kind='annotation'` 的新版本。
7. **人工文字編輯不解除 stale。** 只有 `POST /drafts/{id}/reviews` 帶理由才會把 freshness 改回 current。
8. **合併在預覽階段算完，採用交易只複核。** `merge_service` 產生不可變的 `merge_previews` 一列與 `preview_hash`；`apply_service` 只驗 preview 歸屬、案件版本、hash、組依賴閉包與是否已套用，然後寫版本。昂貴的計算不要搬進採用交易。
9. **有衝突時預覽的候選內容要保留目前版本。** `_Merger` 在衝突分支也會把 current 內容放進 `working`，否則人工整合端點會找不到資源可改。
10. **錯誤碼照 [04 §7](04-API契約.md)。** 已用到的對應：缺欄位或欄位不合規 422 `INVALID_FIELD`；壞 JSON 400 `MALFORMED_REQUEST`；候選越界或基底不符 422 `OUT_OF_SCOPE_PATCH`；引用不存在或必要引用組沒一起採用 422 `INVALID_CITATION`；案件或資源版本過期 409 `REVISION_CONFLICT`；依賴事實已變 409 `DEPENDENCY_STALE`；區塊不在該版本 409 `TARGET_MOVED`；重複採用同組 409 `PROPOSAL_ALREADY_APPLIED`；跨案與不存在一律 404 `RESOURCE_NOT_FOUND`。
11. **身分只從伺服器設定來。** `get_actor_id` 讀 Settings，前端不能指定 actor。要換成真登入就改這個 dependency，不要讓 actor_id 進入請求體。
12. **測試風格**：Arrange-Act-Assert，測試名稱描述行為。新功能先寫測試（RED），再實作。`tests/conftest.py` 有 `mutate`、`create_case`、`create_draft`、`proposal_body` 等 helper，冪等鍵預設自動產生，要測重送才自己指定同一把。

## 4. 已知偏離與待回寫契約

這三個端點的實作語意已回寫 [04](04-API契約.md)，但前兩個仍是階段 A 為了驗證流程而加的暫時入口，不等於正式 run 流程：

| 端點 | 為什麼加 | 之後怎麼辦 |
|---|---|---|
| `POST /api/v1/cases/{case_id}/drafts` | 沒有草稿就測不了編輯與 diff | 正式流程改由抽文／生成建立；目前保留作階段 A 入口 |
| `POST /api/v1/cases/{case_id}/proposals` | 契約的提案由 run 產生，那是階段 B | 階段 B 接真 run 後，這個 fixture 入口應限測試用或移除 |
| `POST /api/v1/cases/{case_id}/drafts/{draft_id}/reviews` | 保存一個新版本並把 freshness 改回 current | 已與 04 對齊；規則引擎完成後再加入必要分析未完成時的阻擋 |

其他缺口：

- **`EvidenceRepository` 已能查證，但尚未接進提案。** 它會核對 r3 manifest／artifact hash，只索引 `index_eligible=true` 的 3,002 個 chunk，支援同案家族排除，並由 page／line／char spans 重建 quote；來源時效一律標 `snapshot_only`。現有合成 `POST /proposals` 尚未呼叫這層，所以 `evidence_records` 仍是 null／`unverified`／`unknown`，採用時仍列 `unverified_evidence_ids`。下一步是由工具 adapter 寫入程式實算結果，不准由呼叫端自稱已查證。
- **同一區塊的字元級自動合併沒做**，依 [03 §6.1](03-後端SQLite與版本合併.md) 規則 3 保守視為衝突。完整文件衝突也是整份判定。
- **沒有 `PATCH /selections`**，引用是否齊備只靠修改組依賴閉包把關。
- **`gate_result` 與 `source_span` 兩種 TargetRef 只驗形狀**，不驗目標存在，因為沒有 analyses 與來源快照表。
- **沒有規則引擎。** 事實變動時保守把所有草稿標 stale，這是 H01 只能標 `PASS＊` 的原因。
- **沒有 run、SSE、jobs、submissions、case_documents 表。** 刻意不預先建用不到的結構。

## 5. 下一步：階段 B

目標依 [05 §2](05-實作順序與驗收.md)：接本地 read／search／open 工具與真實活動事件，完成來源卡、規則 trace 解釋與缺證回覆。**這一階段結束時 AI 仍不能改正式內容**，只能回答與列出實際讀過的材料。

建議順序，每步都先寫測試：

1. **B0 語料讀取層（已完成）。** r3 `EvidenceRepository` 能以穩定 ID 搜尋／開啟來源、回傳 hash、判定 `source_exists`／`quote_matches`，並排除同案件家族。它是內部類別，尚不會改 case DB。對應 [02 §5.1](02-AI側邊欄與查證編修.md)。
2. **run 與事件表（下一步）。** 新 migration 加 `ai_runs`、`run_events`、`jobs`。run 狀態用 `queued/running/completed/failed/cancelled/needs_input`，事件序號每個 run 單調遞增。對應 [03 §3](03-後端SQLite與版本合併.md) 與 [04 §6](04-API契約.md)。
3. **工具包裝層。** 實作 `read_case_resource`、`read_selection_context`、`search_knowledge`、`open_source`；後兩者包裝已存在的 EvidenceRepository。活動事件由包裝層寫入，不由模型自述；`open_source` 成功才算「已閱讀」，search 命中只算「搜尋命中」。`apply_proposal`、`save_human_review`、`submit_case` **不是模型工具**。對應 [02 §4](02-AI側邊欄與查證編修.md)。
4. **協調器與 intent 路由。** 先用固定假回應完成 `explain` 與 `verify` 兩個 intent。`context_manifest` 在 run 開始時凍結案件、規則與 r3 基底，執行期間只追加真正讀到的證據。缺證時回 `needs_input`，不要補一段看似合理的答案。
5. **聊天端點與串流。** `POST /chat-threads`、`POST /chat-threads/{id}/messages`、`GET /runs/{id}`、`GET /runs/{id}/events`（SSE，支援 Last-Event-ID 補送）、`POST /runs/{id}/cancellations`。重連只補送已保存事件，不重跑模型。
6. **把 fixture 提案入口換成真 run。** 階段 A 的 `POST /proposals` 由 run 產生的提案取代；提案物件與採用鏈不要重做，直接沿用 `proposal_service`／`merge_service`／`apply_service`。

階段 B 完成時應該能把 [05 §3](05-實作順序與驗收.md) 的 A03、A04、A06、A08、S01、S02 從 NOT RUN 改成有依據的狀態。**改狀態時要附實跑證據，不能因為程式寫好了就標 PASS。**

## 6. 已決定事項與剩餘授權

1. **語料固定讀 r3。** r1/r2 保留為歷史證據，不作新證據層來源。r3 只索引 `index_eligible=true` 的 3,002 個 chunk；101 個歷史決定書主文 chunk 以 `historical_outcome_excluded` 排除。法規、標籤與時效仍受 [r3 稽核](../../sysdoc/verification/r3-audit.json) 的限制。
2. **先做 BM25。** 已完成 r3 離線 baseline、同案排除、去重與精確引文定位；不要先加向量。等 dev inputs／gold 完成並量到 BM25 的具體缺口，再決定是否增加 embedding。
3. **尚未授權線上模型。** provider、模型名稱、額度與費用都未驗證。下一批先用固定假回應把 run、事件與工具紀錄做真；不得把假回應記成模型輸出。
4. **身分維持單人 stub。** 目前只驗同一 actor 下案件隔離；多人權限與 V08 的跨使用者部分尚未驗證。若下一步需要正式登入或組織角色，必須另向使用者取得授權與需求。
