# 資料前處理與切分交接規格

版本：v1.0｜日期：2026-09-12｜對象：資料前處理負責人、後端與驗收負責人

**任務：把官方 PDF 整理成能檢索、能引用、能回查、能重建的資料集，並交付不洩漏答案的測試資料。** 完成定義不是「成功產出 JSON」或「全部做完 embedding」，而是後端可以依穩定 ID 取得原文、定位來源、辨別版本與資料品質。

本文件是實作與交接規格，**尚未實作新的前處理工具、產出新資料或完成全庫人工驗收**。下列新路徑、schema、指令與門檻是本次提出的交付契約；既有狀況另行標示。切分長度是待開發集驗證的起始參數，不是已證明的最佳值。

## 1. 分工與依據

| 負責人 | 應交付 | 邊界 |
|---|---|---|
| 資料負責人 | 語料清冊、逐頁抽文、切段、來源座標、人工標註、評估樣本、schema、驗收報告、可重跑工具 | 不代替法律判準引擎作新案件結論；不接手前端畫面 |
| 後端負責人 | 載入與查詢、索引、案件隔離、評估時排除來源案件、API adapter | 不擅改資料 ID、條號與欄位語意 |
| 前端負責人 | 來源預覽、缺值／待確認提示、推薦勾選與草稿畫面 | `selected` 是案件操作狀態，不能寫回共用語料 |
| 驗收負責人 | 原文核對、凍結標準答案與 holdout、簽收報告 | 區分「資料前處理通過」與「模型／法律判斷正確」 |

系統方向依 [北極星指南手冊](北極星指南手冊.md) §4、§8、§9；法律規則背景查 [開發文件](Reference/開發文件.md)。現有 `app/` 是參考實作，不是新資料契約的限制。舊文件的 `docs/開發文件.md` 現位於 `docs/Reference/開發文件.md`。

本工作不重做法律考證；標註有歧義時保留原文、列待確認，不把模型推論寫成法律事實。既有文件若與可見 PDF 不符，記錄差異並依原文重新驗證。

## 2. 本次已確認的資料現況與必修問題

本次盤點基準：Git `55b39f3` 的程式與當下本機資料。PDF 計數、文字抽取與 JSON 統計為本次執行；未代表完成每頁視覺檢查。

| 類別 | 原始位置 | PDF 數 | 既有 JSON 筆數 |
|---|---|---:|---:|
| 歷史訴願決定書 | `data/歷史訴願決定書/` | 101 | 101 |
| 法規 | `data/相關法規/` | 11 | 1,976 |
| 行政函釋 | `data/行政函釋/` | 10 | 10 |
| 司法院釋字及行政判解 | `data/司法院釋字及行政判解/` | 19 | 19 |
| 合計 | | **141** | **2,106** |

掃描合計 **731 頁**；其中 **7 頁**抽取後非空白字元少於 20，含 1 頁零字。這只是人工檢查名單，不能直接宣稱是空白頁或需要 OCR。

必須處理以下問題：

1. **附加條號漏切。** `app/src/parsers.py` 只用整數條號切分；已視覺核對《廢棄物清理法》PDF 第 1 頁「第 2-1 條」，並確認既有 JSON 把它塞進第 2 條內容。全庫掃到 238 個附加條號標題候選：廢棄物清理法 4、建築法 18、民法 214、行政執行法 1、行政程序法 1。這是候選數，須排除重複標題等情況後驗收；**不得把 1,976 或 1,976 + 238 直接當成正確總數**。
2. **來源路徑失效。** 2,106 筆既有 `source_file` 在本機均無法解析到檔案。需改用儲存庫相對路徑及檔案雜湊，不能沿用其他人的絕對路徑。
3. **頁碼與行號遺失。** 現行 `extract_text()` 直接串接全文，沒有輸出逐頁來源座標。
4. **標籤來源錯置。** 現行程式從檔名取案件類型、款別與結果；開發文件 §1.2 已記錄檔名款別與正文不一致。檔名只能作交叉檢查。
5. **缺段落不能直接補空。** 101 件中有 70 件 `facts` 為空；要區分「無獨立事實標題」「抽取失敗」「本來未記載」，不能捏造事實段。
6. **檢索內容被截斷。** `build_index.py` 把事實／理由各截前 800 字，函釋／判解截前 1,200 字；後段法律理由可能沒被索引。
7. **舊建庫指令可能覆寫成空庫。** `build_kb.py` 預設資料根目錄是 repo 根目錄，卻直接找其下四個中文分類目錄；實際分類在 `data/`。掃不到檔案仍會寫出空 JSON。
8. **舊建索引入口不適合作為交付命令。** `build_index.py` 有兩個 `__main__` 區塊，執行後會再次建全庫；`statutes` 也沒有實際強制關閉向量。不得假設舊 README 所述「只建法規 BM25、不耗額度」已由程式保證。

## 3. 先區分兩種「切分」

- **文件切段（chunking）**：把同一份文件拆成可檢索的條文／理由段，但保留整份文件與來源關係。
- **評估資料切分（split）**：把案件家族分到開發與保留測試集，避免同案的其他段落、合成輸入或答案出現在評估輸入／檢索候選中。

兩件事都要做。不能把同一份決定書的 chunk 隨機分散到不同 split，再宣稱測到了新案件的效果。

## 4. 交付目錄與資料層

以下為新工作建議目錄；先在 `data/processed/releases/<release_id>/` 輸出，驗收後才由後端切換讀取位置。

```text
data/                                      # 既有官方 PDF 原封保留
data/processed/releases/<release_id>/
  manifest.json                            # 設定、版本、hash、計數、發布狀態
  documents.jsonl                          # 一份文件一筆
  pages.jsonl                              # 一頁一筆，含原始行與座標
  sections.jsonl                           # 條文、主文、理由等完整結構單元
  chunks.jsonl                             # 檢索單元；全部可回到 sections/pages
  annotations.jsonl                        # 人工核對的欄位、標籤與證據
  citations.jsonl                          # 文件中的法條／函釋／判解引用關係
  duplicates.jsonl                         # 重複檔、同案關係、處置理由
  review_queue.jsonl                       # 待確認／失敗項目與定位
  qa_report.json
  qa_report.md
data/evaluation/<eval_version>/
  splits.json                              # 依案件家族凍結的分組
  dev/inputs.jsonl
  dev/gold.jsonl
  holdout/inputs.jsonl
  holdout/gold.jsonl                        # 僅供評估程式讀取
  regression/                              # 已公開的固定回歸案例
scripts/preprocess/                        # 新前處理工具及說明
tests/preprocess/                          # parser、座標、資料契約回歸測試
```

UTF-8、LF；JSONL 一行一筆，不加註解。發布檔案依固定 ID 排序。公開且可再散布的資料產物可納版控；受限原件、個資衍生檔與評估答案依權限分開保存，不因是 JSON 就自動提交。索引與 OCR 暫存不納版控。

`holdout/gold.jsonl` 即使存於專案中，也不得被應用程式的載入器、prompt 或索引建置器讀取；評估執行環境另行隔離，避免只靠開發者自律。

## 5. 按順序執行的處理流程

### 步驟 A：清冊、去重與不可變原件

1. 列出全部 PDF，相對路徑從 repo 根目錄開始；記錄大小、SHA-256、頁數、類別、來源批次。外部新增語料另存來源 URL、取得時間、授權／存取條件。
2. 原檔不改名、不清字、不覆蓋。相同 SHA-256 的檔案只抽一次，但保留所有路徑別名。
3. 同案不同版本、重新掃描、裁判更正不能只因案號相同就刪除；建立同案家族，保留版本差異。
4. 文字相似只標記 `near_duplicate_candidate`，人工確認後才能合併。大量共同法條／制式用語不等於同一案件。
5. 禁止零輸入成功：輸入目錄不存在、141 份基準批次無故少檔、全類別零筆，必須非零退出並留下原因。

### 步驟 B：逐頁抽取與原文座標

先用既有 PyMuPDF 抽取文字層，每頁保留頁寬高、文字行、bounding box、原始抽取順序與選定閱讀順序。文字過少、亂碼、順序不合理、表格錯位列人工檢查；確認是影像頁，或文字層損壞且無法可靠恢復時，才補 OCR。不得把「抽不到字」直接判為「原文無內容」。

座標規約固定如下：

- `page` 是 **PDF 物理頁碼，從 1 起算**；印刷頁碼另存 `printed_page_label`。
- `line` 是抽取版本固定的頁內行號，從 1 起算；不是模型自己計算的行號。
- `bbox = [x0, y0, x1, y1]` 使用 PyMuPDF 該頁座標系；保留頁旋轉與尺寸，前端按比例換算。
- `char_start`／`char_end` 是該原始行字串的 Unicode code point 範圍，0 起算、左含右不含；不是位元組，也不是 JavaScript UTF-16 索引。
- OCR 行必須標記 `extraction_method: ocr`、引擎版本、覆核狀態。未覆核的關鍵數字或條號不得進正式可引用資料。

跨頁原句要保留多個 `source_spans`，不能只寫「p1–p3」而無法確認引用到底在何處。PDF 版面不同，不可一律按 y/x 排序就當閱讀順序正確；先用小批次確認單欄、表格與頁腳處理。

### 步驟 C：清理，但原文與檢索文字分開

保存三種內容：`raw_text` 是固定抽取器的輸出；`quote_text` 從原始來源範圍重建；`search_text` 才能做檢索正規化、加標題與別名。

允許在 `search_text` 統一換行、全形空白、連續空白與已記錄的名稱別名。頁首、頁尾、下載日期、URL 可排除於檢索，但保留原行並標記排除原因。不能刪除所有獨立數字：PDF 中的 `1`、`2` 可能是項次。

**禁止改動否定詞、但書、例外、日期、金額、條號、文號、遮罩字元；禁止用 LLM「補順」原文。** `污染／汙染` 的統一只能在別名或檢索層，引用原文照錄。OCR 更正要記原值、更正值、座標、覆核人與時間。

`quote_text` 的拼接規則固定為：各 span 按閱讀順序取原行指定範圍，以 `\n` 連接；不可再偷偷壓縮空白。需要可讀性整理時使用另一個 display 欄位。每個索引字元都應能追溯到原文或明確的新增 metadata。

### 步驟 D：結構辨識與文件分類

文件種類由官方分類目錄提供初值，再以正文檢查。釋字解釋與行政法院判決在同一資料夾，也要用 `document_subtype` 區別。

結構辨識依「版面＋獨立標題行＋上下文順序」，不是看到內文提及「理由」就切段。每個非空白行都要歸到一個 section 或明確的排除清冊，不能默默遺失。

決定書沒有「事實」標題時，保留 `section_type: unsectioned` 或理由段中的事實敘述。`facts` 的缺值原因填 `no_explicit_section`；之後若抽取事實欄位，仍需指回實際段落，不得偽造一個原文標題。

### 步驟 E：依文件種類切段

| 類型 | 完整父層單元 | 可檢索子段 | 必須保留的上下文 |
|---|---|---|---|
| 法規 | 一個版本的一條法條 | 短條整條；長條按項、款、目 | 法名、完整條號、項款層級、前導句、但書、版本 |
| 訴願決定書 | 一份案件及其主文／事實／理由／教示段 | 理由按編號論點；事實按完整事件敘述 | 段落種類、敘述角色、同案 ID、相鄰段落 |
| 行政函釋 | 一份函及主旨／說明／結論 | 按說明一、二、三等語意單元 | 機關、文號、日期、主旨與被解釋問題 |
| 判決／裁定／釋字 | 一份文件及相應主文／理由等 | 按裁判論點或解釋理由段 | 法院／機關、案號、文件子類型、說話者 |

**法規特別規則：**

- `第 15 條`、`第 15-2 條`、`第十五條之二` 必須能辨識；後兩者可在正規化欄位映射為 `15-2`，保留原始寫法。
- 切點必須是實際條文標題，不能把內文「依第 15 條規定」當成新條。目錄、附件、沿革與章節標題分開標記。
- 條號用字串 `article_key`，不使用只有整數的 `article_num` 當唯一鍵。
- 同一條的項／款不得編成新的法條。刪除條文保存原文與 `article_status: deleted`，不當有效規範推薦；狀態不明則 `unknown`。
- 法條修正日期、公布日期、生效日期是不同欄位；文件的整部法規修正日不等於每一條都在當天修正。
- PDF 快照不保證今天仍有效。`is_current` 未經另行查證為 `null`；歷史版本不存在就列缺口，不從新版本反推舊法。

**案件特別規則：**

- 分開 `appellant_claim`、`authority_response`、`adjudicator_reasoning`；無法識別填 `unknown`。承辦機關引述某人的說法，不代表機關採納。
- 事實、理由與主文不混切；引用法條的區塊與套用到個案的論述分段後，以 `context_section_ids` 保留關聯。
- 多款並列、部分不受理／部分駁回保留陣列與分項範圍，不能硬塞成單一款別或單一正反方。
- 歷史主文／結論存於標註與展示資料，預設不進一般事實檢索文字。若後端有特定歷史查詢用途，另建明確用途的索引。

**長度起始設定：**以清理後 Unicode 字元數計，不稱為 token。一般子段目標 **400–800 字**，**1,200 字是重新檢查切點的軟上限**；完整短條／短段不強迫補滿。先按法律結構，再按句界；不可從句中硬切、截掉後半或把但書單獨留下。

核心子段不重疊，以便檢查全文覆蓋；需要前導句／前項時，使用 `context_section_ids` 或 `context_chunk_ids` 回取，並讓後端計入總輸入長度。超長原子單元無法安全再切時標 `oversize_atomic`，保留全文，由後端分段讀取或轉人工，不靜默截斷。實際 embedding token 上限由選定供應商的 tokenizer／計數介面再檢查，不能把中文字數當精確 token 數。

### 步驟 F：欄位、標籤與引用標註

101 件決定書全部從正文核對案件類型、主文結果與結論引用款別；檔名值另存 `filename_hint` 作差異報告。標註者可讀完整歷史決定書，但這些答案不能混入新案件輸入。

每個抽取事實使用：

```json
{
  "value": null,
  "source_spans": [],
  "confidence": 0,
  "extraction_method": "rule",
  "review_status": "unreviewed",
  "missing_reason": "not_stated"
}
```

有值就附來源；`confidence` 是抽取器的啟發式分數，不是法律正確機率。人工確認用 `review_status` 表示。未見代理人記載不等於 `has_agent: false`；文件沒有資料時保留 `null`。

缺值原因限定：`not_stated`、`no_explicit_section`、`unreadable`、`parse_failed`、`ambiguous`、`conflicting_sources`、`not_applicable`。前處理本身無法決定是否適用時，不可用 `not_applicable` 掩蓋未知。

日期同時保存 `date_raw`、`calendar`、`date_iso`、`date_precision` 與來源。`date_iso` 使用西元 `YYYY-MM-DD`；只知民國年度時不要補 1 月 1 日，`date_iso: null` 並另存年度。處分、送達、收文、決定日期各自存，不能互相代填。

每筆引用關係保存：來源文件／段落、`citation_raw`、正規化法名／條號／項款、被引用文件或法條 ID、解析狀態。`resolved` 必須有實際目標；庫內沒有舊法或判解時填 `unresolved`，保留引文而不編造目標。`前條／前項` 無法可靠解析就保留原文並列待確認。

## 6. 後端可直接使用的最小資料契約

### 6.1 ID 與版本

- `document_id`：以該 PDF 位元組的 SHA-256 產生不含結果暗示的穩定 ID；改路徑不改 ID，原件內容改變則產生新文件版本 ID。
- `case_family_id`：跨版本、同案與合成樣本共用的去重／評估分組鍵；不是分類標籤，不從檔名結果推導。
- `section_id`：`document_id + extraction_version + segmentation_version + section ordinal` 的可重現 ID；結構切點變動必須更新 segmentation version。
- `chunk_id`：`section_id + chunking_version + source spans + quote hash` 的可重現 ID；切點或內容改變必須換 ID。
- 法條另有 `law_id + article_key + source_version_id`。未知生效日不妨礙識別資料快照，不能把未知版本冒充現行版。

舊 `doc_id` 如需相容，提供 `legacy_id_map`，不可要求新系統繼續依賴錯誤條號。不同版本的 ID 不得指向不同文字卻仍沿用同一引用快取。

### 6.2 四個核心實體

| 檔案 | 必填內容 | 用途 |
|---|---|---|
| `documents.jsonl` | `schema_version, document_id, case_family_id, document_type, document_subtype, source_file, source_sha256, source_origin, page_count, extraction_version, review_status` | 來源登錄；無案件家族的法規可用 `case_family_id: null` |
| `pages.jsonl` | `document_id, extraction_version, page, width, height, rotation, raw_text, lines, extraction_method, review_status` | 每行含 `line, text, bbox`；span 由這裡回查 |
| `sections.jsonl` | `section_id, document_id, segmentation_version, section_type, ordinal, source_spans, quote_text, metadata, review_status` | 保存完整法律單元；metadata 依類別有條號／敘述角色等 |
| `chunks.jsonl` | `chunk_id, section_id, document_id, quote_text, search_text, source_spans, context_section_ids, index_eligible, quality_flags, chunking_version` | 供後端索引；是否准入必須明確 |

抽取 metadata 中的事實依 §5 步驟 F 包裝；系統產生的 ID、計數、類別枚舉不需假造來源信心值。完整 schema 由資料負責人以 JSON Schema 或既有 Pydantic 交付，包含上述輔助檔案，不能只有範例 JSON。

`source_spans` 的每個元素包含 `document_id, extraction_version, page, line, char_start, char_end`；同一行多個非連續片段需分別列出。範圍必須落在 `pages.jsonl` 對應原行內。引用者使用相同欄位結構，不各自發明「p1 L3」字串格式。

枚舉初版：`document_type` 使用 `decision/statute/interpretation/precedent`；`review_status` 使用 `unreviewed/verified/needs_review/rejected`；`source_origin` 使用 `official_batch/public_extension/synthetic`。`index_eligible` 是布林值，隔離紀錄必為 `false`。manifest 另列 schema／抽文／結構切分／chunking／別名表版本、設定 hash、每個產物的 hash、輸入／成功／失敗／隔離數，以及 `draft/partial/validated` 發布狀態。

`metadata` 至少覆蓋：

- 法規：`law_id, statute_name, article_key, paragraph_path, source_version_id, amendment_date, promulgation_date, effective_from, effective_to, is_current, article_status`。
- 案件：`case_no, decision_date, case_type, outcome_parts, art77_paragraphs, speaker_role`；多款／複合結果用陣列，未知為 `null`。
- 函釋／判解：`issuing_authority/court, doc_no/case_no, issue_date, title, document_subtype`。

下面只示意引用的關係，不是可上線資料：

```text
chunk → section → document → 相對 PDF 路徑及 SHA-256
  └── source_spans → extraction_version + page + line + 字元範圍
```

後端回傳前端時可把座標轉成「第 2 頁，第 3–6 行」，但須同時保留結構化引用。排序分數、`selected`、案件當次狀態不屬於不可變的語料紀錄。

## 7. 評估資料的切分與答案隔離

### 7.1 分組流程

目前沒有需要訓練新模型的已確認任務，**不先硬切 train／validation／test 三份**。先建立固定回歸案例、開發集、保留測試集：

1. 先完成同案去重與關聯，產生 `case_family_id`。同案的原文、chunk、重掃版本、合成輸入全部同組。
2. 已被拿來設計規則的 10 件期間算式及展示案例放 `regression`／`dev`，不能事後稱為未見測試。
3. 對剩餘案件家族，以固定 seed `42`、穩定排序，按案件類型與正文結果盡量分層，約 **80% dev／20% holdout**；以實際家族數為分母。
4. 稀有類型、複合案無法兼顧分層時，逐項記錄配置，不複製到兩邊。報告每類實際 n，0 或極少樣本不能宣稱有效評估。
5. 保存分組演算法版本、ID 清單、seed、選擇理由與檔案 hash。切段、清理、分類規則只在 dev 調整，holdout 用於固定方案的最終評估。
6. 看過 holdout 結果後再改方案，要記一次新的評估循環；不要將反覆調整後的成績描述成首次保留測試。

### 7.2 合成新進件與標準答案分開

官方資料沒有原始訴願書與配對行政處分書，從決定書反向整理的輸入一律標 `synthetic: true`，保留 `derived_from_document_id` 於評估控制檔。

合成輸入只能使用可歸屬於申請人主張或原處分內容的敘述；從理由段摘到的文字不因此自動變成「訴願理由」。需要人工逐段確認說話者與決定前可知性。假設／虛構的配對欄位明標 `mock`，不能冒充 PDF 證據。

採明確 allowlist 建構模型輸入，例如 `appeal_text`、`disposition_text` 及兩者有來源的欄位；不要把整筆 JSON 傳給模型再要求它忽略答案。

禁止送入輸入：決定書要旨、主文結果、機關最終論結、決定書「相關法條」答案欄、檔名款別／結果、標準答案、來源案號、帶答案的檔案路徑。原處分書本來引用的法條可以使用，但必須真有該來源，不能從決定書答案欄搬過去。

`gold.jsonl` 可保存正文已驗證的類型、款別、教示、引用法條與證據；每筆含 `label_status`。尚未確認的標籤不得進正確率分母，並另外報排除件數。

### 7.3 檢索時也要排除同案答案

評估某件合成輸入時，後端必須從**所有會被呼叫的索引與快取**排除其 `case_family_id`：不只相似案例搜尋，還包括「先找案例再推薦法條」的間接路徑。該案的主文、摘要、理由、標籤與衍生樣本都不能被召回。

**開發期間整個 holdout 家族集合都不得進索引或生成範例。** v1 最終 holdout 評估也固定使用 dev／regression 案例候選庫，不把其他 holdout 案件的答案放回候選庫。開發集評估則在這份候選庫中再排除當次 query 的家族。評估 runner 在送入模型前剝除來源 ID 等控制欄位，但必須先用它們完成排除。

其他允許的歷史案例可作檢索候選，但不得用其數量掩蓋同案重複；Top 5 以去重後文件／案件計數，不是 5 個 chunk。法規、函釋、判解使用獨立版本清冊，不能因與測試題相關就任意剔除正常公共知識，也不能偷偷加入答案衍生文檔。正式展示的全量索引與評估索引必須分開命名與快取。

若做歷史時點回測，再加發布日期／可取得時間的過濾；若使用全庫快照，報告就寫「固定快照檢索測試」，不能聲稱當年已可取得全部資料。

## 8. 品質門檻與驗收方式

先跑全量自動檢查，再人工回到 PDF 核對。以下是 **v1 交付門檻**，不是目前已達成的結果。

| 檢查 | 通過條件 | 失敗處置 |
|---|---|---|
| 原件清點 | 基準 141 份、731 頁全部可對帳；新增／排除有明細 | 阻擋發布 |
| 雜湊與路徑 | 所有來源相對路徑可解析，hash 相符 | 阻擋發布 |
| 全文覆蓋 | 每個非空白行／字元歸屬結構單元或明示排除；例外列出 | 不得悄悄掉段 |
| ID／引用 | 無重複主鍵、懸空外鍵；span 範圍合法，100% 可重建 quote | 阻擋相關紀錄准入 |
| 法條邊界 | 11 部法規全部對帳；附加條號獨立、無相鄰條串接 | 阻擋法規庫發布 |
| 關鍵標籤 | 101 件正文結果／款別／類型全部覆核；不明項明列 | 不明標籤不作 gold／硬過濾 |
| 低文字／異常頁 | 本次 7 頁逐頁視覺判定，後續新增異常全部處理 | 非空內容未恢復則隔離 |
| 規則關鍵字 | 不得遺失否定、但書、日期、金額、條號；抽樣零重大錯誤 | 發現一件就修規則並擴查同模式 |
| 防洩漏 | 同案跨 split 為 0；模型輸入與所有召回路徑排除答案 | 阻擋評估發布 |
| 可重現 | 同原件／設定跑兩次，核心資料 ID 與內容 hash 相同 | 追查排序、版本、非確定生成 |

人工檢查最少包括：11 部法規所有條號與段落邊界；101 件關鍵標籤；全部待確認項；另抽 **20 份文件**核對完整引用與切段，其中決定書 8、法規 4、函釋 4、判解 4，涵蓋長文、跨頁、缺標題、複合結果與三大重點類型。20 份是文字品質抽驗，不能取代全庫條號與標籤核對。

`review_queue` 每項要有 `item_id, document_id, source_spans, issue_type, severity, status, resolution, reviewer, reviewed_at`。無錯誤不是沒有 log；必須產出空清單與零件數報告。關鍵錯誤可先隔離，但未達完整基準時發布狀態只能是 `partial`，不得聲稱全庫驗收通過。

解析輸出不等於已核對正確。兩次重跑一致的檢查排除 `run_started_at` 等執行時間欄位，核心內容比較方式記在 manifest。含模型／OCR 的步驟要凍結其輸出及版本，否則不能宣稱完全可重現。

### 必須隨工具交付的回歸測試

- `第 2 條 → 第 2-1 條 → 第 3 條` 三筆互不吞併；中文附加條號、跨頁續條、刪除條文各一例。
- 理由中提到「主文」或「第 X 條」不造成錯誤切段；無事實標題不補假段。
- 多款併列、複合主文、申請人說法與機關結論分離。
- 頁腳數字可排除，但法條項次與日期／金額不丟失；跨頁 quote 可逐字還原。
- 同 hash 異路徑、同案不同版本、同案合成樣本不跨 split。
- 缺來源、重複 ID、非法 span、零輸入、空法規庫一律失敗；未發布產物不能蓋掉上次可用版本。
- 沒有 API key／斷網仍可完成清冊、抽文、切分與資料驗收；向量不是前處理成功的必要條件。

## 9. 檢索品質檢查與資料不足的回報

資料負責人準備 query／gold，後端執行索引比較；先用 BM25 做可重現基線，再按同一份 dev 比較新切分與舊截斷方法。不要一邊換語料、一邊換模型、一邊換切段，最後無法解釋改善來自哪裡。

- 法條、函釋、判解分開報資料涵蓋率與 Recall@5。gold 引用不在庫內仍計入涵蓋缺口；另報只針對可檢索 gold 的召回，明列兩種分母。
- 法條按正規化法條／版本 ID 去重；函釋、判解與案例按文件／案件家族去重。不能用多段同文件充滿 Top 5。
- gold 空集合與未核對案件分開標示 `not_evaluable`，不補成 0 分或 100%。報告列 query 數、gold 數、候選數與排除數。
- 案例分桶使用已核對的案件類型／程序屬性；多款、複合案不簡化成錯誤標籤。只用同桶作候選條件不代表已證明語意相關；排序品質仍需人工相關性標註。
- 三大類型的桶大小以**查詢排除自身後的獨立案件數**計算。五個 chunk 或五篇不相關文件都不算達標；資料不足就如實回傳數量與警告。
- 分類、程序判準、日期計算與草稿是否正確，由對應後端測試驗收；資料團隊提供可定位 gold，不以「chunk 可讀」代替功能驗證。

既有手冊提到的 65 件多法規案等數字，需在新資料重建後重算；本次不能直接視為新的評估分母。合成樣本結果不能直接外推真實訴願書準確率。

## 10. 可直接分派的工作順序

### 第一個交付點：契約與 12 份小批次

先交 schema、清冊與試跑報告，再處理全庫。小批次包含 4 份法規、4 件決定書、2 份函釋、2 份判解；涵蓋附加條號、長條、跨頁、無事實標題、複合主文。

指定納入《廢棄物清理法》（已確認附加條號問題）、《民法》（長文／附加條號多）、114 年第 21 件複合案、以及 96 年 8 月 8 日公寓大廈管委會函釋（第 2 頁抽文為零）。其餘從清冊選取並記 ID，避免每次試跑換樣本。

交後端確認：ID、引用座標、缺值語意、欄位映射、哪些紀錄可以索引。前端取得 3–5 筆去識別範例即可先做來源展示；不用等待全庫向量化。

### 第二個交付點：全量資料與正文覆核

完成 141 份逐頁處理、法條邊界核對、101 件關鍵標籤覆核、低文字頁處置。交全量資料、例外名單、diff 統計及可重跑說明；禁止只傳一個沒有版本的壓縮檔。

### 第三個交付點：評估包與後端串接

交分組清單、合成輸入／gold 隔離、固定回歸例、資料品質報告。後端提供讀取 adapter 與排除同案的檢索測試；雙方用同一 `release_id` 核對來源預覽、全文回取及去重後 Top K。

索引若要向量化，再記模型名稱、向量維度、text hash、chunking version 與 release ID；斷網時 BM25 可以獨立工作。不同 release 的 metadata 與向量不混用；重建失敗不替換正式索引。

### 第四個交付點：聚焦擴充

依北極星 D3，既有資料管線驗收後，再擴充洗錢防制、廢棄物清理、空氣污染的函釋／判解及必要案例。新增資料維持相同清冊、版本、去重與來源規則，與官方提供批次分開報告。先確認覆蓋的是哪些缺少的法律問題，不以堆文件數交差。
