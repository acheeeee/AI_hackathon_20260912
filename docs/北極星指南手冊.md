## 1.2 【衝突一】文本分類模型 vs 規則分類——真正的問題不是方法，是資料洩漏

| 立場 | 說法 |
|---|---|
| 命題文件 | 「並使用**文本分類模型**自動判斷案件類型」 |
| 開發文件 §6.2 | 「規則優先：`要旨` 標頭 → 案件類型（實測 94/101）…**不需要訓練分類模型**」 |

表面上是「模型 vs 規則」之爭，但真正的問題在別的地方：

> **`要旨` 是「訴願決定書」的標頭欄位，而訴願決定書是這個系統要產出的東西。**
> 系統實際運作時，手上只有訴願書和行政處分書，**沒有決定書，因此沒有 `要旨`**。

這在機器學習裡叫**資料洩漏（data leakage）——用只有在答案裡才看得到的資訊去預測答案**。94/101 這個數字衡量的其實是「檔名標籤和要旨標頭一不一致」，不是「從訴願書輸入能不能分對類型」。這兩者是完全不同的問題，而後者從來沒被測過。

**裁決**：

1. **`要旨` 只能當標準答案（label），不能當輸入特徵（feature）。** 這是硬規則，違反就等於沒有評估。
2. 分類的**輸入**只能用推論時真的拿得到的東西：訴願書全文 ＋ 行政處分書的「處分依據法規」。後者最可靠——處分書一定會寫「違反廢棄物清理法第 X 條」，法規名稱直接映射到案件類型。
3. 實作採**規則優先 ＋ 語言模型補強**：規則（處分依據法規 → 類型映射）跑得到就用規則；規則落空（處分書沒抽到依據法規）才交給語言模型判斷，且必須回傳信心值。
4. **對命題的交代**：命題要的是「自動判斷案件類型」這個**功能**，不是「訓練一個模型」這個**手段**。我們有可量測的分類功能，選擇規則+模型混合而非訓練模型，理由是 101 筆樣本不足以訓練、且規則可稽核可解釋——這在政府場域是優點不是妥協。簡報要主動講這個理由，不要迴避命題用了「模型」兩個字。

## 1.3 【衝突二】「不做事實查核」vs 命題的「事實調查、卷證比對」

| 立場 | 說法 |
|---|---|
| 命題文件 背景 | 「訴願決定書之撰擬不僅涉及**事實調查**，嚴謹的**卷證比對**」 |
| 會議記錄 畫面⑤ | 「**不做事實查核**…我們就是當他的事實是事實」 |

**裁決：兩者其實相容，但會議的說法必須精確化，否則簡報會被問爆。** 要拆成兩件不同的事：

| | 系統做不做 | 為什麼 |
|---|---|---|
| 事實**真偽**調查（他到底有沒有闖紅燈） | **不做** | 卷證、現場照片、舉發資料不在系統裡；而且訴願審查的標的本來就不是重新調查事實 |
| 卷證**一致性比對**（訴願書的主張 vs 行政處分書的記載，有沒有對不上） | **要做，而且是高價值輸出** | 這正是會議自己決定要把行政處分書拉進來配對的理由 |

**精確化後的表述**（簡報與文件一律用這句）：

> 系統不驗證事實真偽，只做兩件事：**文件間的一致性比對**，以及**「已認定事實」與「所引法條構成要件」之間的涵攝檢查**。

「比對出不一致」本身要當成一個明確的輸出項目丟給承辦人看——兩份文件講的不一樣，是承辦人最需要被提醒的事情之一。

## 1.4 【衝突三】§77 是主幹 vs 命題完全沒提 §77

命題文件的 4 大標準化工具（擷取分類／法規推薦／相似案例／草稿生成）**全部指向實體審查輔助，通篇沒有出現「訴願法第 77 條」或「程序審查」**。但開發文件和會議記錄都把 §77 當成系統主幹。

**這是本次交叉比對最重要的發現，如果處理錯了會直接偏題。**

**裁決：§77 是流程主幹，不是交付主體。**

- 命題的 12 條需求是**必要條件**——每一條都要做到可驗收，少一條就是交付不完整。
- §77 判準引擎是**差異化加分項**，不能排擠掉上面任何一條。
- 但 §77 **不是偏題**，理由要講清楚：開發文件實測，樣本 101 篇裡有 **70 篇是不受理案**，而不受理決定書的「理由欄」本體就是 §77 的論理。**你要做命題需求 R9（決定書草稿生成），就必然要生成 §77 論理。§77 引擎是 R9 的必要前提，不是額外發明的東西。**

簡報定位句：

> 命題要我們生成決定書草稿。我們去看了 101 份真實決定書，發現其中 70 份的理由欄核心就是訴願法第 77 條的程序論理。所以我們沒有把 §77 當成附加功能——它是「草稿生成」這件事本身的主要內容。

# 第二部　北極星：不可動搖的設計約束

## 2.1 系統是什麼、不是什麼

| 是 | 不是 |
|---|---|
| 訴願審議**承辦人**的內部輔助工具 | 民眾自助查詢服務（做成這樣即偏題） |
| 產出**有出處的草稿** | 產出決定 |
| 把承辦人腦中的隱性判斷變成**有紀錄的判斷** | 取代承辦人的判斷 |
| 抽不到就說抽不到 | 猜一個看起來合理的答案 |

**使用者（沿用開發文件 §2.1）**：主要對象是新北市法制局訴願審議承辦人；次要是訴願審議委員會委員；第三是法制局主管。**訴願人與一般民眾明確不是使用者。**

## 2.2 四條紅線

1. **系統不做決定，只交出有出處的草稿。** 決定權 100% 在承辦人與委員會。
2. **「不確定」是一等公民輸出。** 抽不到事實、或落在實質法律判斷（§77 第 3、8 款），一律標示轉人工，不准猜。
3. **每個事實主張都要有出處。** 抽出的欄位標頁碼行號，推出的結論標條文。抽不到就回 `null` 並且 `confidence: 0`——這一條現有 `app/` 完全沒實作，重做時必須補上。
4. **推論時拿不到的資訊，不准當成輸入。** 見 §1.2 的資料洩漏問題。任何用決定書欄位當特徵的設計，一律退回。

## 2.3 錯誤成本不對稱原則（新增）

**這是本手冊相對於三份來源文件新增的設計原則，而且它應該凌駕於一般的準確率考量。**

訴願系統的兩種錯誤，代價差好幾個數量級：

| 錯誤 | 後果 | 可逆性 |
|---|---|---|
| 把**應受理**的案子判成不受理 | 剝奪人民訴願權 → 行政法院撤銷 → 工具失去機關信任 | **幾乎不可逆** |
| 把**應不受理**的案子放進實體審查 | 承辦人多花時間審一次 | 完全可逆 |

**設計後果（硬規則）**：

- 任何 §77 判準引擎的閘門，**寧可漏放（判 NOT_TRIGGERED）也不要誤擋（判 TRIGGERED）**。
- 期間計算只要有任一輸入欄位是 `null`，**一律回 `INSUFFICIENT_EVIDENCE`，不准用預設值補**。
- 驗收指標不能只看整體準確率，必須分開報「應受理案被誤判為不受理」的件數——這個數字的目標是 **0**，不是「低」。
- 開發文件 §4.1 已經抓到一次這類錯誤（把「上報機關錯誤」誤當成不受理事由，實際上訴願法 §14 IV 規定那只影響提起日認定）。**這種錯誤會再發生，靠的是這條原則和測試，不是靠小心。**

## 3.1 全景

```
  輸入：訴願書 PDF ＋ 行政處分書 PDF
        │
```

## 3.2 哪幾層是檢索、哪幾層不是

> **檢索增強生成（RAG，Retrieval-Augmented Generation）**——先從文件庫撈出幾段相關文字，再連同問題一起交給語言模型，請它照著撈到的內容回答，目的是讓模型不要憑空編造。這是目前文件問答的預設做法，**這場比賽多數隊伍都會用**（開發文件 §7.3 實測主辦的 AWS 工作坊教材裡 RAG 相關關鍵字密集出現）。

| 模組 | 是 RAG？ | 理由 |
|---|---|---|
| M1 擷取 | 部分 | 語言模型抽欄位，但輸出受強制格式約束，不做判斷 |
| M2 分類 | ✗ | 規則優先，模型只做備援 |
| M3 爭點識別 | 部分 | 需要語言模型定位爭點，但候選範圍由 §77 款別/處分法條先框住 |
| M4 摘要關鍵字 | ✗（是生成，不是檢索） | 輸入就是本案文件，不需要外部檢索 |
| M5 一致性比對 | ✗ | 兩份文件的欄位對照 |
| **M6 法規推薦** | **✓** | 就是檢索 |
| **M7 相似案例** | **✓** | 檢索，但軸是款別不是案件類型（開發文件 §4.2 已實驗證明） |
| M8 時效警示 | ✗ | 兩份文件中繼資料的日期比較，這個事實沒有被寫在任何文件裡 |
| M9 草稿：事實欄 | ✗ | 模板填空 |
| **M9 草稿：理由欄（實體案）** | **✓** | 就是生成 |
| M10 §77 判準 | ✗ | 純函式 |
| M11 期間計算 | ✗ | 日期算術 |
| M12 稽核 | ✗ | 紀錄 |

**上台時不要宣稱「我們不是 RAG」——一問就破。** 正確定位句（沿用開發文件 §3.2）：

> 我們不是不用檢索，是不讓檢索做它做不到的事。一般做法是「檢索完，讓模型判斷」；我們是「先判斷，再決定要檢索什麼」——模型只負責舉證，不負責判斷。可以這樣做，是因為**答案的結構是法律先寫好的**：訴願法第 77 條就白紙黑字列著八款，不需要用檢索去「發現」它。

## 3.3 為什麼不沿用現有 `app/`

不是因為程式碼寫得不好，是因為**骨架不在**：

| 缺什麼 | 實測 |
|---|---|
| §77 判準引擎 | `grep art77` = 0、`GateResult` = 0 |
| 期間計算（含在途期間、行政程序法 §48 IV/V） | `在途` = 0 |
| 稽核層 | `audit` / `稽核` = 0 |
| 紅線三的 `confidence` 欄位 | `confidence` = 0 |
| 教示生成（命題 R10） | `教示` = 0 |
| 摘要／關鍵字（命題 R12） | `關鍵字` = 0 |
| 爭點識別（命題 R3） | 僅有欄位痕跡，無模組 |
| 多案並行的狀態隔離 | 模組層級全域 `dict`，多分頁互相覆蓋 |

會議記錄敲定的六畫面流程，主幹是 §77 的「過／不過」分流——而那個分流在現有程式碼裡根本不存在。**在缺骨架的系統上長肉，比重建貴。**

**可以沿用的**（當成參考而非基礎）：`src/providers.py` 的 Provider 抽象設計（把模型呼叫集中在一個檔案，換供應商只改一處）、`src/parsers.py` 的 PDF 欄位抽取經驗、`data/kb/*.json` 已建好的知識庫（1,976 條法條已解析完成，可直接重用，省掉重跑）。

## 3.4 技術棧與部署（決策 D4）

| 層 | 選擇 | 理由 |
|---|---|---|
| 後端 | **Python + FastAPI** | 法律規則引擎與日期算術用 Python 最直接；FastAPI 自動產生 API 文件，前後端對契約時省事 |
| 前端 | **Vue 3 + TypeScript + Vite + Pinia + Vue Router** | 延續既有經驗；TypeScript 的型別定義可以直接對應第四部的資料契約，契約改動時前端會編譯失敗而不是靜默出錯 |
| 狀態儲存 | **SQLite** | 案件狀態必須持久化（§7 紅線：不得用全域變數）。101 件規模不需要 PostgreSQL；SQLite 零設定、單檔、可進版控，符合「最簡單但真的能動」的原則 |
| 檢索索引 | **本地檔案快取**（關鍵字索引 + 向量快取） | 這個語料規模不需要向量資料庫服務。外部服務會增加 Demo 當天的失敗點 |
| 模型供應商 | **抽換層封裝，預設 Gemini** | 見下 |
| 測試 | **pytest** | §9.4 要求 M10／M11／M9.3／M8 四支必須有測試才准合併 |

**明確不用**：圖資料庫（Demo 環境跑不起來）、向量資料庫服務（語料規模不需要）、任何需要在主辦電腦上安裝執行環境的方案。

### 模型供應商抽換層（這一層是設計重點，不只是工程整潔）

所有模型呼叫集中在單一模組，其餘程式碼一律透過它取得供應商，**不准在別處直接 import 任何廠商的 SDK**。

```
src/providers.py
  get_provider() → Provider
      .embed(texts)    向量化（含頻率限制自動重試）
      .generate(...)   文字生成（強制結構化輸出）
```

這件事在這個專案有超出工程整潔的意義：

> 開發文件 §7.3 實測，主辦的技術工作坊由 AWS Professional Services 主講，等於在推雲端模型服務。但**訴願卷證是個資**，把個資送上雲端在政府場域會被質疑（附錄 A #3 仍待確認）。
>
> 模型層可抽換，讓這個張力從「弱點」變成「設計特點」——簡報可以直接說：**「模型層是可替換的。要雲端就接雲端，要地端就換地端，法律判斷的部分本來就不經過模型，所以換誰都不影響判斷正確性。」**

**降級路徑（必須保留）**：沒有模型額度或呼叫失敗時，檢索自動退回純關鍵字模式，**查詢路徑不得中斷**。擷取與生成類功能則明確回報「模型不可用」，不得靜默失敗或填假資料。

# 第四部　資料契約

**所有欄位的共同規則**：凡是從文件抽出來的事實，一律包成 `{ value, source, confidence }`；抽不到就 `null` 且 `confidence: 0`。**不准用空字串、不准用預設值。**

## 4.1 CaseFacts（M1 輸出）

沿用開發文件 §5.1，**新增粗體欄位**：

```jsonc
{
  "case_id": "1147101471",
  "appellant":  { "value": "林○如", "source": "訴願書 p1 L3", "confidence": 0.95 },
  "authority":  { "value": "新北市政府警察局蘆洲分局", "source": "訴願書 p1 L5", "confidence": 0.9 },
  "disposition": {
    "date":       { "value": "112-11-12", "source": "處分書 p1", "confidence": 0.95 },
    "doc_no":     { "value": "1124430434", "source": "處分書 p1", "confidence": 0.9 },
    "type":       { "value": "書面告誡", "source": "處分書 p1", "confidence": 0.85 },
    "legal_base": { "value": "洗錢防制法 §15-2", "source": "處分書 p1", "confidence": 0.9 },
    "fine_amount": null
  },
  "service": {
    "date":   { "value": "112-11-12", "source": "送達證書", "confidence": 0.9 },
    "method": { "value": "本人簽收", "source": "送達證書", "confidence": 0.9 }
  },
  "filing": {
    "received_date": { "value": "114-10-20", "source": "收文條碼", "confidence": 0.95 },
    "received_by":   { "value": "原處分機關", "source": "收文章戳", "confidence": 0.8 }
  },
  "appellant_domicile": { "value": "新北市", "source": "訴願書 p1 L4", "confidence": 0.9 },
  "has_agent":       { "value": false, "source": "訴願書全文", "confidence": 0.8 },
  "agent_domicile":  null,

  "appellant_claim": { "value": "主張處分時為黃燈…", "source": "訴願書 理由欄 p2", "confidence": 0.85 },
  "relief_sought":   { "value": "請求撤銷原處分", "source": "訴願書 p2 L10", "confidence": 0.9 },

  "case_type": {
    "value": "違反洗錢防制法事件",
    "derived_from": "disposition.legal_base",
    "method": "rule",
    "confidence": 0.95
  }
}
```

**欄位語意補充**：

- `service.method` 三種值：`本人簽收` / `寄存送達` / `補充送達`——決定期間起算日（寄存送達依行政程序法 §74 另有生效日規則）。
- `filing.received_by` 三種值：`原處分機關` / `受理訴願機關` / `其他機關`。**第三種不是不受理事由**（訴願法 §14 IV），只是改用該機關收受日當提起日。這是開發文件 §4.1 已經抓到的法律錯誤，重做時不准再犯。
- `case_type.method` 兩種值：`rule`（由處分依據法規映射）/ `llm`（規則落空時的備援）。**`要旨` 不得出現在 `derived_from`。**
- `appellant_claim` / `relief_sought` 是新增欄位，來自會議記錄對「事實欄 vs 理由欄」的釐清：事實欄是裁罰機關認定的事實，**理由欄才是訴願人自己的主張**。命題 R1 的「訴願理由」指的是後者。

## 4.2 GateResult（M10 輸出）

沿用開發文件 §5.2，語意不變：

```jsonc
{
  "gate_id": "art77_para2_overdue",
  "legal_basis": ["訴願法§77(2)", "訴願法§14 I", "訴願法§14 III",
                  "訴願法§16 I", "行政程序法§48 IV"],
  "required_facts": ["service.date", "filing.received_date",
                     "appellant_domicile", "has_agent"],
  "outcome": "TRIGGERED",
  "confidence": 1.0,
  "computation": {
    "start_date": "112-11-13", "period_days": 30, "transit_days": 0,
    "raw_due_date": "112-12-12", "adjusted_due_date": "112-12-12",
    "adjustment_reason": null,
    "filed_date": "114-10-20", "days_overdue": 678
  },
  "evidence_refs": ["送達證書", "訴願書收文條碼"],
  "rule_version": "sha256:a3f2...",
  "short_circuit": true
}
```

`outcome` 五種狀態：

| 狀態 | 意思 | 畫面 | 允許進入不受理草稿？ |
|---|---|---|---|
| `NOT_TRIGGERED` | 這款不成立 | 綠 | — |
| `TRIGGERED` | 這款成立 → 不受理 | 紅 | 是 |
| `NOT_APPLICABLE` | 本案不適用（例如個人訴願人 vs 第 5 款法人代表） | 灰 | — |
| `INSUFFICIENT_EVIDENCE` | 缺必要事實 | 黃 | **否，轉人工** |
| `NEEDS_HUMAN` | 屬實質法律判斷（第 3、8 款） | 黃 | **否，轉人工** |

**硬規則**：只有 `TRIGGERED` 能產生不受理草稿。黃燈一律不產草稿，只提供爭點定位與判解檢索結果供承辦人判斷（見 §2.3 錯誤成本不對稱）。

## 4.3 IssueProfile（M3 輸出，新增）

命題 R3 要的「識別主要爭點」。爭點的操作型定義**依路徑而不同**：

```jsonc
{
  "path": "procedural",              // procedural | substantive
  "issues": [{
    "issue_id": "iss_1",
    "statement": "訴願人是否為行政處分之相對人或利害關係人",
    "issue_type": "當事人適格",
    "anchored_to": { "kind": "art77_para", "ref": "訴願法§77(3)" },
    "appellant_position": { "value": "主張其為受處分土地之共有人", "source": "訴願書 p2 L4" },
    "authority_position": { "value": "處分對象為管理委員會", "source": "處分書 p1 L8" },
    "confidence": 0.7
  }],
  "extraction_method": "llm_constrained"
}
```

- **程序路徑**：爭點 = 被觸發（或存疑）的 §77 款別之構成要件爭執點，`anchored_to` 指向款別。
- **實體路徑**：爭點 = 「處分所引法條的構成要件」與「訴願人主張」的交集點，`anchored_to` 指向處分依據法條。
- **紅線**：爭點的兩造立場欄位必須各自帶 `source`。抽不到任一方立場，該爭點不得輸出。

## 4.4 RecommendationSet（M6 輸出）

命題 R4/R5/R6 要求三類，**必須分開回傳、分開驗收**：

```jsonc
{
  "statutes":       [{ "id": "...", "name": "洗錢防制法", "article": "§15-2",
                       "text": "…原文…", "score": 0.83,
                       "amend_date": "113-07-31", "is_current": false,
                       "selected": false }],
  "interpretations":[{ "id": "...", "issuing_authority": "法務部",
                       "doc_no": "法律字第0970000279號", "date": "97-01-29",
                       "summary": "…", "score": 0.61, "selected": false }],
  "precedents":     [{ "id": "...", "court": "最高行政法院",
                       "case_no": "106年度判字第151號", "topic": "行政罰法第5條從新從輕",
                       "score": 0.58, "selected": false }],
  "coverage_warning": "行政函釋語料僅 10 篇，本次推薦之召回率無法保證"
}
```

- `selected` 對應會議記錄畫面⑤的勾選狀態。
- **`coverage_warning` 是必填欄位**，當該類語料規模低於門檻時必須回傳並在畫面上顯示。這是誠實聲明的程式化，不是可選的貼心功能。
- 紅線：每一筆推薦的 `text` 必須是知識庫裡的**真實原文**，抽不到原文的候選一律丟棄，不得由模型補寫。

## 4.5 SimilarCase（M7 輸出）

```jsonc
{
  "bucket": { "art77_para": "77(2)", "case_type": "違反洗錢防制法事件",
              "bucket_size": 3 },
  "cases": [{ "doc_id": "114-07", "year": 114, "case_no": "…",
              "result": "訴願不受理",
              "stance": "against_appellant",   // for_appellant | against_appellant
              "similarity": 0.72,
              "reasoning_skeleton": "…理由欄摘要…",
              "selected": false }],
  "honest_note": "同款別同類型僅 3 件，未達命題建議之 3-5 件上限"
}
```

- `stance` 就是會議記錄講的「正方／反方」：`for_appellant` = 原處分撤銷（訴願人成功）、`against_appellant` = 不受理或駁回。
- **`stance` 是顯示維度，不是硬過濾條件**（見 §1.5 G4）。桶子本來就薄，再切一刀會空。
- `honest_note` 與 `bucket_size` 必填。**寧可回 2 件並說明只有 2 件，也不要為了湊滿 5 件放進不相關的案子。**

## 4.6 DraftDecision（M9 輸出）

沿用開發文件 §5.3，**`origin` 四種值**讓承辦人一眼看出每段的來源：

```jsonc
{
  "outcome_type": "不受理",
  "sections": [
    { "id": "主文",   "text": "訴願不受理。", "origin": "template" },
    { "id": "事實",   "text": "訴願人於…", "origin": "filled",
      "slots": { "service_date": "112-11-12" } },
    { "id": "理由一", "text": "按訴願之提起，應自…", "origin": "template",
      "template_id": "art77_p2_premise" },
    { "id": "理由三", "text": "本件訴願人不服…", "origin": "filled" },
    { "id": "理由四", "text": "…綜上論結…", "origin": "llm",
      "grounded_on": ["statute:訴願法§77(2)", "case:113-03"] },
    { "id": "教示",   "text": "如不服本決定，得於…臺北高等行政法院…", "origin": "rule",
      "rule": "不受理 + 決定年≥112 → 高等行政法院" }
  ],
  "citations": [
    { "text": "訴願法第77條第2款", "path": "data/相關法規/訴願法.pdf", "verified": true }
  ],
  "editable": true
}
```

| `origin` | 意思 | 畫面標示 |
|---|---|---|
| `template` | 固定模板原文 | 不標色 |
| `filled` | 系統把擷取到的事實填進模板 | 淺底，滑過顯示 source |
| `rule` | 規則推導（教示、主文） | 淺底，顯示規則 |
| `llm` | 語言模型生成 | **明顯標示**，且必須帶 `grounded_on` 列出它依據的檢索結果 |

**紅線**：`origin: "llm"` 的段落若 `grounded_on` 為空，該段不得輸出。`citations` 裡 `verified: false` 的引用不得出現在草稿正文。

## 4.7 AuditEntry（M12 輸出）

```jsonc
{
  "case_id": "…", "timestamp": "…", "actor": "system | 承辦人姓名",
  "gate_results": [ /* 含每個 gate 的 rule_version */ ],
  "ruleset_version": "sha256:…",
  "selections": { "statutes": ["…"], "precedents": ["…"] },
  "human_edits": [ { "section": "理由四", "before": "…", "after": "…", "reason": "…" } ],
  "prev_hash": "sha256:…", "entry_hash": "sha256:…"
}
```

> **雜湊鏈（hash chain）**——每一筆紀錄都算出一個固定長度的指紋（SHA-256），並把前一筆的指紋寫進自己裡面。這樣只要有人事後竄改中間任何一筆，後面所有指紋都對不上，竄改就藏不住。

**必須存規則版本雜湊，不只存結論。** 否則規則改版後，「當初這案是依什麼規則判的」就查不回來，稽核鏈失去意義。開發文件 §6.6 已警告：**這是設計要求，不是後續優化，加在後面會很痛。**

# 第五部　模組規格

格式統一：輸入 / 輸出 / 實作 / 紅線 / 驗收。

## M1 文件擷取層

- **輸入**：訴願書 PDF、行政處分書 PDF
- **輸出**：`CaseFacts`
- **實作**：PDF 文字抽取 → 規則抽欄位（日期、文號、機關名這類格式固定的）→ 語言模型補剩下的，輸出強制符合 `CaseFacts` 結構
- **紅線**：抽不到回 `null` + `confidence: 0`，不准推測；每欄必須帶頁碼行號
- **驗收**：對 101 篇決定書反向合成的輸入，各欄位抽取率與正確率分欄報告；`null` 率本身也要報（高 `null` 率不是失敗，是誠實）
- **⚠ 已知資料缺口**：資料集**沒有任何訴願書原件**，只有決定書。Demo 輸入需從決定書的「事實」＋「訴願意旨略謂」段反向合成；行政處分書同樣缺，會議決議用假資料（mock data）示範配對。**簡報上必須主動講。**

## M2 案件分類

- **輸入**：`disposition.legal_base`（主）、訴願書全文（備援）
- **輸出**：`case_type`，含 `method` 與 `confidence`
- **實作**：
  1. 規則：處分依據法規名稱 → 案件類型映射表（洗錢防制法 → 違反洗錢防制法事件，廢棄物清理法 → …）
  2. 規則落空 → 語言模型分類，回傳信心值
- **紅線**：**`要旨` 欄位禁止作為輸入**（見 §1.2）。`要旨` 只能出現在驗收腳本裡當標準答案。
- **驗收**：以 101 篇的 `要旨` 標頭當標準答案，但**輸入只給反向合成的訴願書 + 處分書**。分開報規則命中率與模型備援準確率。**不得再引用 94/101 這個數字**——那是另一個問題的答案。

## M3 爭點識別（新增，命題 R3）

- **輸入**：`CaseFacts`、`GateResult[]`（程序路徑）或處分依據法條原文（實體路徑）
- **輸出**：`IssueProfile`
- **實作**：候選範圍先由結構框住（程序路徑框在被觸發/存疑的款別；實體路徑框在處分所引法條的構成要件），再用語言模型在框內定位兩造立場
- **紅線**：兩造立場各自要有 `source`；抽不到任一方，該爭點不輸出
- **驗收**：標準答案從 101 篇決定書理由欄抽「本件所須審究者為…」「爭點厥為…」「本件應審究者…」等句型；指標為爭點語意命中率（人工判定），**件數少、主觀性高，報告時必須標示這是小樣本人工評估**
- **範圍**：爭點的**視覺化**（心智圖／樹狀圖）維持 P2，非命題要求

## M4 摘要與關鍵字（新增，命題 R12 ＋ 會議畫面②）

- **輸入**：訴願書全文、行政處分書全文
- **輸出**：`{ summary, key_points[], keywords[] }`，每項帶 `source`
- **實作**：語言模型生成，強制每一句摘要對應到來源段落
- **紅線**：**摘要不得出現原文沒有的事實**。關鍵字必須是原文出現過的詞，不得自創。
- **設計理由**（來自會議記錄）：承辦人現行工作習慣就是先掃關鍵字抓重點，系統要延續這個習慣而不是強迫他們改用新方式。**行政處分書才是摘要的主要素材**——訴願書的事實欄通常短而口語，資訊量不足。
- **驗收**：摘要逐句可回溯率（目標 100%）；關鍵字是否全部出現於原文（目標 100%）

## M5 卷證一致性比對（新增，回應 §1.3）

- **輸入**：`CaseFacts` 中來自訴願書與來自處分書的對應欄位
- **輸出**：`{ field, from_appeal, from_disposition, consistent: bool, note }[]`
- **實作**：欄位對照（處分文號、處分日期、處分機關、所引法條、處分內容）
- **紅線**：只報「一不一致」，**不做誰對誰錯的判斷**
- **驗收**：以人工建構的不一致案例（刻意改動文號/日期）測試偵測率

## M6 法規推薦（命題 R4/R5/R6）

- **輸入**：`case_type`、`IssueProfile`、`disposition.legal_base`
- **輸出**：`RecommendationSet`（法條／函釋／判解三類分開）
- **實作**：混合檢索——關鍵字檢索（BM25，一種靠詞頻比對找相關文件的傳統演算法，跑在本地不花錢）＋ 向量檢索（把文字轉成一串數字座標，用座標距離找語意相近的內容）。沒有模型額度時自動退回純關鍵字檢索，**查詢路徑不得中斷**。
- **紅線**：每筆推薦必須附知識庫裡的真實原文；抽不到原文的候選丟棄。語料不足時必填 `coverage_warning`。
- **驗收**：
  - 法條：Recall@5（系統推薦的前 5 條裡，有幾成真的出現在標準答案中）對 `相關法條` 欄位；**分母限定在 65 件多法規案**（36 件只列訴願法的不受理案，這個任務是平凡的，放進分母會灌水）
  - 函釋／判解：標準答案從決定書正文抽出的引用；**目前語料規模下必須同時報出「語料涵蓋率」**，否則 Recall 數字沒有意義

## M7 相似案例（命題 R8）

- **輸入**：`GateResult[]`（款別）、`case_type`
- **輸出**：`SimilarCase`
- **實作**：兩層——
  1. **硬過濾（結構化，不用向量）**：§77 款別 ＋ 案件類型 ＋ 處分類型
  2. **桶內排序（語意）**：過濾後才做相似度排序
- **設計理由**（開發文件 §1.5 實驗）：同款別的論理重疊度 0.319，同案件類型只有 0.167（隨機是 0.137）。**案件類型幾乎不帶訊號**；款別帶強訊號。純語意檢索會沿著「噪音／廢棄物／洗錢」這些表面詞走，等於在一條沒有訊號的軸上檢索。
- **紅線**：桶內不足 3 件時，回傳實際件數並填 `honest_note`，**不得放寬過濾條件去湊數**。近乎重複的決定書要去重（第 6 款內部重疊度 0.703，很可能撈出 5 份幾乎一樣的東西）。
- **驗收**：桶內排序的 Top-K 命中率；**同時報告各桶的實際大小分布**——這是判斷「Top 5 是不是虛的」的唯一方法

## M8 時效與版本警示（命題 R7）

拆成兩個**不同觸發條件**的警示：

| | 觸發條件 | 依據 | 系統動作 |
|---|---|---|---|
| **A. 從新從輕** | 行為日 < 修正日 ≤ **處分日** | 行政罰法 §5 | 提示比較新舊法何者有利於受處罰者 |
| **B. 條次對照說明** | 處分日 < 修正日 < 決定日 | 決定書說理義務 | 提示交代條次變更、說明為何仍適用舊法 |

> **行政罰法 §5 原文**：「行為後法律或自治條例有變更者，適用**裁處時**之法律或自治條例。但**裁處前**之法律或自治條例有利於受處罰者，適用最有利於受處罰者之規定。」
> **從新從輕比較的是「行為時 → 裁處時」，訴願決定日不在比較區間內。** 開發文件 §6.5 已修正過一次這個錯誤（舊版誤寫成 `處分日 < 修正日 < 決定日`），重做時不准再犯。

- **紅線**：兩者都必須**先通過 §77 判準（確認進入實體審查）才觸發**。程序不受理的案子根本不涉及實體法適用。開發文件實測：沒有這道前置條件時，B 規則在 71 件可判定案中觸發 8 件，其中 6 件是不受理案的假陽性。
- **驗收**：以法規修正日期表（開發文件 §1.7）為右表逐案跑；**真實 precision / recall 在沒有法律專家標註前算不出來，簡報不得宣稱數字**。目前唯一人工確認的真陽性是 113 年 #18 洗錢案。

## M9 草稿組裝與匯出（命題 R9/R10/R11）

- **紅線**：`grounded_on` 為空不得輸出

## M10 §77 判準引擎

八款各一個純函式，簽章統一：

```python
def gate_art77_para2(facts: CaseFacts, rules: RuleSet) -> GateResult: ...
```

**§77 是「排除性確認」，不是「八道依序通過的關卡」**——條文寫「有左列各款情形**之一**者」，是「或」的邏輯，任一款成立即不受理。

實作優先序：

| 款 | 判斷性質 | 實作要求 |
|---|---|---|
| 第 2 款 逾法定期間 | 純日期算術 | **完整實作 + 10 件官方算式測試全綠**（這是高光） |
| 第 1、6、7 款 | 機械 | 完整實作 |
| 第 4 款 | 機械偏事實 | 實作，但**樣本僅 3 件，簡報標示無法驗證** |
| 第 5 款 | 機械 | 實作，**樣本 0 件，完全無法驗證，必須明講** |
| **第 3、8 款** | **實質法律判斷** | **一律回 `NEEDS_HUMAN`，不產草稿。這是正確行為，不是偷懶。** |

第 3、8 款合計 24 件（佔不受理案 34%），且論理重疊度最低（0.216 / 0.194），代表每件都要獨立判斷。**「案件結束」的主體永遠是承辦人與委員會，不是系統。**

## M11 期間計算模組

> **全系統最該被獨立、最該有測試的一支。**

```
輸入：送達日、送達方式、收受機關、訴願人住居地、有無訴願代理人及其住居地
輸出：起算日、法定期間、在途期間、原末日、調整後末日、調整理由、是否逾期、逾期天數
```

規則來源（開發文件已從條文原文逐條核對）：

| 規則 | 依據 |
|---|---|
| 次日起算 | 訴願法 §14 I、行政程序法 §48 II |
| 30 日 | 訴願法 §14 I |
| 以機關收受日為準 | 訴願法 §14 III |
| 誤向他機關 → 以該機關收受日為準（**不是不受理事由**） | 訴願法 §14 IV |
| 在途期間扣除（代理人住居受理機關所在地者除外） | 訴願法 §16 I |
| 期間計算準用民法 | 訴願法 §17 |
| 末日為星期日／國定假日 → 次日；星期六 → 次星期一上午 | 行政程序法 §48 IV |
| 不利處分末日「照計」的例外的例外 | 行政程序法 §48 V |
| 寄存送達生效日 | 行政程序法 §74 |

> ⚠ **行政程序法 §48 V 是雙重否定**：不利處分的期間末日遇休息日「照計」，但依第 2、4 項計算「對人民有利者，不在此限」。訴願案的原處分幾乎都是裁罰（不利處分）會落進第 5 項，但「順延」通常對人民有利，於是又被但書拉回第 4 項。
> **這條必須寫成有測試的函式。任何語言模型在這裡都會擲骰子。**

- **驗收**：開發文件 §1.6 的 10 件真實官方算式，屆滿日**逐日一致**，其中 3 件涉及 §48 IV 末日順延（112年#03 星期日順延、113年#03 星期六順延、110年#04 星期六順延）
- **紅線**：任一輸入欄位為 `null` → 回 `INSUFFICIENT_EVIDENCE`，**不准用預設值**（見 §2.3）

# 第六部　前端規格

六個畫面，來自會議記錄的決議，本手冊補上命題需求對應與驗收條件。

## S1 案件列表頁

- **目的**：承辦人進系統第一眼看到「我手上有哪些案子」
- **元素**：案件卡片列表（顯示案號／類型／狀態／最後更新）、狀態篩選、**右上角上傳按鈕**
- **狀態**：`未處理` / `處理中` / `已完成`
- **關鍵決議**：檔案由承辦人**主動選擇上傳**，不是系統把所有檔案一次全列出來（會議明確排除「所有檔案攤在網頁上」的做法）
- **必須支援多案並行**：一個案子處理到一半可以放著，開新的案子（這是 §1.5 G5 要修的）

## S2 案件內容頁

- **目的**：看懂這個案子在吵什麼
- **元素**：訴願書原文、行政處分書原文、**摘要**、**關鍵字**、**卷證一致性比對結果**、下一步按鈕（「開始分析第 77 條」）
- **資料來源**：M1 / M4 / M5
- **對應命題**：R1、R12
- **必須顯示**：每個擷取欄位的 source；`null` 欄位要明確顯示為「未擷取到」而不是留白

## S3 §77 分析結果頁

- **目的**：程序關卡的過／不過分流
- **元素**：八款檢核清單（五種狀態用不同顏色）、**期間計算算式攤開顯示**（起算日／法定期間／在途期間／原末日／調整後末日／調整理由）、每款的 `legal_basis`
- **分流**：
  - 任一款 `TRIGGERED` → S4
  - 有 `NEEDS_HUMAN` / `INSUFFICIENT_EVIDENCE` → **轉人工佇列**（不產草稿，只給爭點與判解）
  - 全部 `NOT_TRIGGERED` → S5
- **關鍵決議**（會議）：八款的勾／叉**是規則檢核結果，不是 AI 判斷**——這點與開發文件一致，畫面上要標示清楚

## S4 不受理草稿頁（不過分支）

- **元素**：草稿全文（依 `origin` 分色）、右側八款檢核結果對照、**可編輯**、**可下載**
- **對應命題**：R9、R10、R11
- **硬性要求**（會議原話）：「一定要可編輯」

## S5 法條與相關案例頁（過分支）

- **元素**：三類推薦分頁（法條／函釋／判解）＋ 相似案例（標示正方/反方）＋ **每項可勾選** ＋ 時效警示 ＋ 爭點摘要
- **順序決議**（會議）：**先法條、後案例**。理由是訴願書本來就會寫出被依哪一條裁罰，系統先推薦對應法條，再拿該法條的正反案例佐證。
- **對應命題**：R3、R4、R5、R6、R7、R8
- **必須顯示**：`coverage_warning` 與 `honest_note`——語料不足時要誠實說，不能假裝滿的

## S6 決定書草稿頁

- **元素**：事實欄 ＋ 理由欄 ＋ 教示，依 `origin` 分色，`llm` 段落要能展開看 `grounded_on`、**可編輯**、**可下載**
- **對應命題**：R9、R10、R11

## S7 狀態機

```
未處理 ──上傳──► 已擷取 ──分析77──► ┌ 不受理草稿 ─► 已完成
                                    ├ 轉人工佇列 ─► （人工處理）
                                    └ 實體推薦 ──勾選──► 決定書草稿 ─► 已完成
```

**每個狀態都綁 `case_id`**，不得用全域變數傳遞（現有 `api.py` 的做法會讓多分頁互相覆蓋，重做時必須修掉）。

# 第八部　知識庫與資料管線

## 8.1 現有語料清點（實測）

| 語料 | 檔數 | 已解析 | 對應命題需求 | 評估 |
|---|---|---|---|---|

| 相關法規 | **11 部** | **1,976 條** | R4 法條推薦 | 這 11 部法規涵蓋完整，可用 |
| 行政函釋 | **10 篇** | 10 筆 | R5 函釋推薦 | **嚴重不足** |
| 司法院釋字及行政判解 | **19 篇** | 19 筆 | R6 判決推薦 | **嚴重不足** |

## 8.2 語料擴充（P1，不是「下一輪」）

**命題文件明文授權**：「*不限以上資料，參賽者可自行從現行政府既有公開統計網站上選取蒐集相關資料運用。」

既然 R5/R6 是命題明文要求、而現有語料只有 10 / 19 篇，**擴充語料不是加分項，是把命題需求做到可用的前提**。

**擴充範圍（決策 D3）：聚焦三大案件類型，不做全面爬取。**

命題文件自己指出最大宗案件類型是**洗錢防制法、廢棄物清理法、空氣污染防制法**。擴充只針對這三類，理由是投報率：這三類佔案量最大，擴充後直接改善 Demo 會用到的案子；全面爬取會把時間花在 Demo 根本不會碰到的類型上，而且爬取失敗的風險隨範圍線性上升。

| 順位 | 來源 | 取什麼 | 解決什麼 |
|---|---|---|---|
| 1 | 司法院裁判書查詢系統 | 三大類型的行政訴訟判決 | R6 判解推薦（目前 19 篇） |
| 2 | 法務部主管法規查詢系統 | 三大類型相關的行政函釋 | R5 函釋推薦（目前 10 篇） |
| 3 | 新北市法制局訴願決定書公開查詢系統 | 三大類型的歷史決定書 | R8 相似案例的桶太薄（目前每桶 2–3 件）；順帶改善「樣本非真實案量分布」 |

> 順位 3 的網址來源：開發文件 §10 發現四份 PDF 結尾殘留查詢網址，URL 參數帶結構化欄位（`K1=不受理&K2=逾期`），可以直接依款別與結果查詢。

**停止條件**（避免無限擴充）：三大類型的相似案例桶，**每桶達到 5 件以上即停**。命題要求的是「前 3-5 個最相似案例」，桶內有 5 件就足以支撐這個需求；超過的收益遞減。

**擴充時的硬規則**：

- 只取公開資料，遵守各站台的使用條款與存取頻率限制
- 每筆保留來源網址與擷取日期
- 新語料與官方提供語料**分開標記**，驗收時要能分開報數字——否則會分不清「效果變好」是因為方法好還是因為偷加資料

## 8.3 建置流程

```
data/*.pdf ──解析──► kb/*.json ──索引──► 混合索引（關鍵字 + 向量）
                                          └ 無模型額度時自動退回純關鍵字
```

`kb/*.json` 進版控（可重現、可 review）；向量索引快取不進版控（可重建）。

# 第九部　驗證計畫

## 9.1 防洩漏規則（最高優先）

**任何評估腳本，輸入端不得出現只在決定書裡才有的欄位。** 具體禁用清單：

| 欄位 | 只能當 | 不能當 |
|---|---|---|
| `要旨` 標頭 | 標準答案 | 分類輸入 |
| `主文` | 標準答案 | 任何模組輸入 |
| `相關法條` 欄 | 標準答案 | 檢索輸入 |
| 決定書「綜上論結」句 | 標準答案（款別） | 判準輸入 |
| 檔名標籤 | **都不行** | 開發文件實測款別錯 10%、類型錯 7 件，**一律以正文為準** |

## 9.2 分模組指標

| 模組 | 指標 | 標準答案 | 可測件數 | 注意 |
|---|---|---|---|---|
| M1 擷取 | 各欄抽取率 / 正確率 / `null` 率 | 人工標註 | 抽樣 20 | `null` 率要報，不是缺點 |
| M2 分類 | 準確率（**輸入不含要旨**） | `要旨` 標頭 | 101 | **不得再引用 94/101** |
| M3 爭點 | 語意命中率（人工） | 理由欄「所須審究者」句 | 小樣本 | 標示主觀性 |
| M4 摘要 | 逐句可回溯率 / 關鍵字原文命中率 | 自動查核 | 全部 | 目標 100% |
| M6 法條 | Recall@5 | `相關法條` 欄 | **65（多法規案）** | 36 件單一法規案排除於分母 |
| M6 函釋/判解 | Recall@5 ＋ **語料涵蓋率** | 正文引用 | 全部 | 語料不足時 Recall 無意義 |
| M7 相似案例 | Top-K 命中率 ＋ **桶大小分布** | 同款別同類型 | 70 | 桶大小是判斷 Top5 虛實的唯一依據 |
| M8 時效警示 | 觸發件數（**不報 precision/recall**） | 法規修正日期表 | 71 | 無專家標註前不得宣稱數字 |
| M9 教示 | **逐字一致率** | 決定書教示原文 | ~86 | 2 種變體 |
| M10 §77 | 各款準確率 | 正文「綜上論結」句 | 70 | **第 4 款 3 件、第 5 款 0 件無法評** |
| M11 期間 | 屆滿日**逐日一致** | 決定書載明屆滿日 | 10 | 含 3 件 §48 IV 順延 |
| 全鏈 | 引用忠實度：草稿每條引用是否真實存在於知識庫 | 自動查核 | 全部 | **防編造的硬指標** |

## 9.3 不對稱錯誤指標（必報）

除了上表，**必須單獨報告一個數字**：

> **應受理案被誤判為不受理的件數。目標值是 0。**

這個數字不能被整體準確率吸收掉（見 §2.3）。101 篇裡有 31 篇是進入實體審查的案子（駁回 15 ＋ 撤銷 15 ＋ 複合 1），這 31 篇跑完 §77 判準後，**任何一件出現 `TRIGGERED` 都是必須修的缺陷，不是可接受的誤差**。

## 9.4 測試分層

| 層 | 對象 | 要求 |
|---|---|---|
| 單元測試 | M10 八款函式、M11 期間計算、M9.3 教示規則、M8 觸發條件 | **這幾支必須有測試才准合併**；M11 以 10 件官方算式為驗收 |
| 整合測試 | API 端點、擷取→判準→草稿的資料流 | 每條路徑（不受理／轉人工／實體）各一 |
| 端到端測試（E2E，模擬真人從頭到尾操作一次） | S1→S6 完整流程 | 三條路徑各一 |

# 第十部　建置順序

因為是全部重做，順序本身就是設計決策：**先建骨架與最可驗證的部分，再長功能。**

## 10.0 「全覆蓋 + 單點做深」的操作型定義（決策 D2）

D2 不是一句態度，是每個模組的完成標準不同。實作時照這張表判斷「做到什麼程度算做完」：

| 深度 | 標準 | 適用模組 |
|---|---|---|
| **做深**（唯一一個） | 有單元測試、對得上官方算式、**評審可以當場拿手機驗算**、算式每一步攤在畫面上 | **M11 期間計算**（10 件官方算式逐日一致） |
| **做實** | 有測試、有驗收數字，但不強求當場驗算 | M10 §77 判準、M9.3 教示生成、M8 時效警示 |
| **做到可演示** | 功能可跑通、有輸出、有誠實標示，指標可報但不強求漂亮 | M1–M7、M9.1/9.2/9.4、M12、S1–S6 |

**紅線**：「做到可演示」**不等於**「可以造假」。所有紅線（出處、`confidence`、`null`、`coverage_warning`、`honest_note`）在任何深度都必須遵守——**寧可演示時顯示「語料不足，僅 2 件」，也不要湊數。**

依 D1（還有數天以上），下面階段 0–5 全部執行。

## 階段 0：地基
- 資料契約（第四部全部）先寫成型別定義，前後端共用
- 知識庫重建（可直接重用現有 `kb/*.json`，1,976 條法條已解析完成）
- **完成定義**：型別檔可被前後端 import，知識庫可查詢

## 階段 1：可驗證的核心（優先，因為它最能證明系統是對的）
- **M11 期間計算** + 10 件官方算式測試全綠
- **M10 §77 判準引擎**（第 2 款完整；1、6、7 款完整；3、8 款回 `NEEDS_HUMAN`）
- **M12 稽核層**（此時加，不要等後面）
- **完成定義**：`pytest` 全綠；31 件實體案跑 §77 無任何誤判 `TRIGGERED`（§9.3）

## 階段 2：擷取與理解
- **M1 擷取層**（含 `confidence`，這是現有程式碼缺的紅線）
- **M2 分類**（防洩漏版本）
- **M4 摘要關鍵字**、**M5 一致性比對**
- **完成定義**：丟一份合成訴願書進去，`CaseFacts` 各欄有值或明確 `null`，每欄有 source

## 階段 3：檢索與推薦
- **M6 法規推薦**（三類分開）、**M7 相似案例**（款別硬過濾）、**M8 時效警示**
- **M3 爭點識別**
- 語料擴充（§8.2）
- **完成定義**：三類推薦分開可驗收；桶大小分布可報告

## 階段 4：草稿與前端
- **M9 草稿組裝**（含教示規則、`origin` 標示、docx 匯出）
- **S1–S6 六畫面** ＋ 狀態機 ＋ case_id 綁定
- **完成定義**：三條路徑（不受理／轉人工／實體）都能從 S1 走到底

## 階段 5：驗收與誠實聲明
- 跑完第九部全部指標，產出數字表
- 更新誠實聲明（§11），把跑出來的實際限制寫進去

## 10.6 時間盒降級路徑（依 D1 目前**不啟用**）

> 保留此節作為「期限突然提前」時的停損依據。正常情況下走階段 0–5，不要提前套用這裡的砍法。

若可用時間不足以走完階段 0–5，**砍的順序**（從後往前砍，不要平均砍）：

1. 先砍 **M3 爭點識別**、**M5 一致性比對**（命題有要求但可用簡化版本交代）
2. 再砍 **語料擴充**，改為在畫面上誠實顯示 `coverage_warning`
3. 再砍 **S1 多案並行**，降為單案流程
4. **絕不砍**：M11 期間計算 + 10 件測試（這是最可驗證的高光）、M10 第 3/8 款轉人工（這是政府採用的關鍵）、稽核層（後加很痛）、Demo 備援錄影

**停損點**：若主線路徑（上傳 → §77 → 草稿）尚未端到端走通，立刻停止開發，把已完成部分錄影＋做成投影片。**有備援影片的半成品能得分；沒備援影片的完整系統當機就是零分。**

## 禁止在簡報上講的話

- 🚫 「69% 的訴願案是程序不受理」——70/101 是出題方抽樣模板的比例（每年 14/20），不是新北市真實案量。評審席可能有訴願審議委員，一講就破。
  - **可以講**：「本樣本 70/101 為程序不受理；樣本為出題方均衡抽樣，不代表實際案量分布。」
- 🚫 「案件分類準確率 94%」——見誠實聲明 #5。
- 🚫 「我們不是 RAG」——七層裡三層是檢索，一問就破。
- 🚫 任何時效警示的 precision / recall 數字——沒有專家標註。

## 可以講、而且無懈可擊的

- 命題文件官方數字：**訴願案量自 110 年 1,238 件增至 114 年 1,566 件**（引用命題文件，不是我們的推估）
- **程序審查是訴願法強制的前置關卡。100% 的案件都必須先確認 §77 八款無一成立，才能進入實體審查。** 這是條文結構（先程序、後實體），不是統計推論。
- 期間計算 **10/10 與官方算式逐日一致**（含 3 件末日順延）
- 教示生成逐字一致率（實測後填入）
