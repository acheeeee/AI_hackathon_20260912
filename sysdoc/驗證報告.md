## 2. r1 的驗證器盲點

既有 `do_validate()` 只執行 13 項檢查。它驗 section quote，沒有驗 chunk quote；依 manifest 的計數判斷基準，沒有逐檔確認目前路徑與 hash；「全文覆蓋」項固定加 PASS 並報告未歸屬清單筆數。人工待辦存在仍可能標 `validated`。

本次獨立檢查額外發現：

- 3,106 chunks 全部缺少交接契約要求的 `chunking_version`。
- 所有 141 documents 的 review status 是 `unreviewed`；101 annotations 的 505 個欄位均未人工覆核。
- annotations 只有 `case_no/doc_no/decision_date/appellant/original_authority`；沒有完成要求的正文類型、結果、款別 gold。
- 101 個決定書的 `case_family_id` 全空，評估目錄不存在。
- 675 citations 全為 `unresolved`，0 個有 target。這本身符合「不要捏造目標」原則，但不能聲稱引文解析已完成。
- 7 個低文字頁仍 open；21 個 `index_eligible=true` chunks 的 spans 觸及這些頁。其可引用性未經人工確認。
- 2,214 個法條 section 缺多項規格 metadata；此數目未經全庫人工邊界核對，不能當正確法條總數。
- 沒有交付完整 schema、設定 hash／產物 hash、案件家族 split 與符合規格的評估包。

因此結論是 **r1 尚未通過完整資料交接，可以復用原件、頁／section 資料及重現流程，但不能直接放行全量 RAG ingestion**。原 release 與舊 QA 檔完全保留；這份報告補上舊驗證器未覆蓋的證據。

## 3. 重跑方法與安全邊界

所有完整重跑都在 `/tmp/ai-hackaton-audit/` 的複製程式目錄，輸出也是暫存 release。原始 PDF 用 symlink 指向已 hash 核對的檔案，沒有改寫 PDF。沒有執行會改寫正式 r1 的 `validate --release r1`。

### 當前布局測試

在暫存 repo 放入 `data/raw` symlink，原樣執行：

```bash
<backend-python> -m scripts.preprocess.run all --input data/raw --release current
```

結果分類全為 unknown，無 section／chunk，exit 1、partial。原因是 `_category_of()` 只取 `data/` 後第一層，所以取到 `raw` 而非中文類別；另外掃到不屬 r1 的 12 份進件。

### 原布局重現

依 r1 的 141 個 source hash，把各原件 symlink 到暫存 repo 的原 `data/<分類>/...` 路徑，然後各跑兩次：

```bash
<preprocess-python> -m scripts.preprocess.run all --input data --release pre-env-a
<preprocess-python> -m scripts.preprocess.run all --input data --release pre-env-b
```

原前處理環境（Python 3.9.6、PyMuPDF 1.26.5）兩次 8 個 JSONL 均與 r1 完全相同。backend 環境（Python 3.12.14、PyMuPDF 1.24.9）得到另一個穩定但不同的版本；結果不是同一份 release。manifest 的 release ID 本來就不同，因此重現 hash 比對以 8 個核心 JSONL 為準。

這證明 r1 可在原條件重現，**不代表**它的 chunk 定位、法律標註或完整驗收正確。沒有用重現成功掩蓋契約失敗。
